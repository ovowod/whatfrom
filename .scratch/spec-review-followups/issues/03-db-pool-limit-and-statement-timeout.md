# DB connection pool 상한과 쿼리 timeout이 없다

Status: done
Category: enhancement
Source: Spec 리뷰 — `docs/superpowers/specs/2026-09-03-whatfrom-design.md` §8

## 문제

spec §8은 "PostgreSQL — 커넥션 풀 상한, 쿼리 타임아웃"을 요구한다. 그런데 `make_engine`은 `pool_pre_ping`만 설정한다. pool 크기는 SQLAlchemy 기본값(5 + overflow 10)에 맡겨져 있고, statement timeout은 없다. 이 항목을 미루거나 바꾼 spec은 없다. F11-a §14는 timeout을 "바꾸지 않는 것"이라고만 적었다.

F11-a의 동시성 제한(`RecommendationLimiter`)과 pool 크기가 어떤 관계인지도 정해지지 않았다.

## 위치

- `src/whatfrom/core/db.py:9-10`

## 완료 조건

- pool 크기와 statement timeout을 설정으로 명시한다. 기본값을 정한 근거를 남긴다.
- timeout을 넘긴 쿼리가 어떻게 처리되는지 정한다. 현재 README는 "DB 오류는 복구 처리에 포함되지 않는다"고 적고 있다.
- 다룰 범위가 아니라고 판단하면, design spec에서 그 결정을 기록한다.

## Agent Brief

**Category:** enhancement
**Summary:** DB pool 크기를 설정으로 노출하고, API engine에만 statement timeout을 건다.

**Current behavior:**
engine 생성 함수는 `pool_pre_ping`만 설정한다. pool 크기는 SQLAlchemy 기본값에 암묵적으로 맡겨져 있다. 쿼리 timeout은 없다. API 서버와 CLI 배치(collect, index 등)가 같은 함수를 쓴다.

**Desired behavior:**
- `Settings`에 `db_pool_size`(기본 5), `db_max_overflow`(기본 10), `db_pool_timeout_seconds`(기본 30), `db_statement_timeout_ms`(기본 5000)를 추가한다. pool 기본값은 지금 동작과 같다.
- engine 생성 함수가 pool 값을 받는다. statement timeout은 선택 인자로 받는다.
- API app은 statement timeout을 적용한 engine을 쓰고, CLI 배치는 timeout 없이 쓴다. 긴 upsert와 색인 때문이다.
- timeout을 넘긴 쿼리는 지금의 DB 오류와 똑같이 처리한다. 즉 별도 복구 없이 500이 된다.
- design spec §8의 PostgreSQL 항목을 이 결정에 맞게 고친다. 값의 근거와 "pool 크기는 부하 측정 뒤 다시 본다"는 점을 적는다.

**Key interfaces:**
- `Settings`의 새 필드 네 개. 환경 변수로 덮어쓸 수 있다.
- engine 생성 함수: pool 인자와 선택적인 statement timeout.

**Acceptance criteria:**
- [ ] API engine의 연결에서 `SHOW statement_timeout`이 설정값을 돌려준다(DB 테스트).
- [ ] CLI가 쓰는 engine에는 statement timeout이 없다.
- [ ] 설정을 지정하지 않으면 pool 크기가 지금과 같다.
- [ ] 전체 테스트와 `make lint`가 통과한다.

**Out of scope:**
- DB 오류를 저하 응답으로 바꾸는 것.
- pool 크기 튜닝과 부하 재측정.
- session factory 공용화(issue 11). 두 issue는 같은 파일을 고치므로 순서대로 작업한다.
