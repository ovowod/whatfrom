# "repo:tag" 문자열을 곳곳에서 다른 방식으로 쪼갠다

Status: done
Category: enhancement
Source: Standards 리뷰 — Primitive Obsession, Duplicated Code (판단)

## 문제

이미지 참조 `"repo:tag"`를 다루는 방식이 위치마다 다르다.

- `verify.py:102`와 `cli.py:231`은 `split(":", 1)`로 쪼갠다.
- `cli.py:353`은 `partition(":")`으로 쪼갠다.
- `retrieval.py:310`은 f-string으로 조립한다.

이미지 실재 여부를 확인하는 조회도 두 곳에 거의 똑같이 들어 있다. `select(ImageTag.id).where(repository==, tag==)` 형태다.

## 위치

- `src/whatfrom/recommend/verify.py:102-108`
- `src/whatfrom/cli.py:231`, `src/whatfrom/cli.py:353-362`
- `src/whatfrom/search/retrieval.py:310`

## 완료 조건

- 작은 `ImageRef` type(parse/format)을 두거나, 실재 여부를 조회하는 helper를 하나 공유한다. 둘 중 하나를 고른다.
- 쪼개는 규칙이 한 곳에 있다.

## Agent Brief

**Category:** enhancement
**Summary:** `"repository:tag"` 문자열을 쪼개는 helper와 이미지 실재 여부 조회를 한 곳에 둔다.

**Current behavior:**
이미지 참조 문자열을 위치마다 다르게 다룬다. recommend 검증은 `split(":", 1)`, eval의 accept 처리는 `split`, eval의 추천 확인은 `partition`으로 쪼갠다. 그리고 "DB에 이 repository:tag가 있는가" 조회가 recommend 검증과 CLI eval에 같은 모양으로 중복돼 있다.

**Desired behavior:**
- `"repository:tag"`를 `(repository, tag)`로 나누는 함수 하나를 `whatfrom.core`에 둔다. 모든 위치가 이 함수를 쓴다. 콜론이 없는 입력도 지금과 같이 처리한다. 위치마다 다르게 처리하고 있다면, 리팩터링 전에 지금 동작을 테스트로 고정한다.
- 이미지 실재 여부 조회는 recommend 검증 쪽 함수 하나로 모으고, CLI eval이 그 함수를 호출한다. CLI는 stage를 조합할 수 있으므로 계층 규칙에 맞다.
- `Recommendation.image`와 API schema의 `image: str`은 바꾸지 않는다.

**Acceptance criteria:**
- [ ] 코드에서 이미지 참조를 `split(":", 1)`이나 `partition(":")`으로 직접 쪼개는 곳이 helper 하나뿐이다.
- [ ] `ImageTag` 실재 여부 조회가 한 곳에만 있다.
- [ ] 전체 테스트(계층 테스트 포함)와 `make lint`가 통과한다.

**Out of scope:**
- `ImageRef` type 도입이나 공개 schema 변경.
- 문자열 조립(`f"{repository}:{tag}"`) 쪽 변경.
