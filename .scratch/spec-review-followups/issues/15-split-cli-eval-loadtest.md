# cli.py가 평가·부하 로직까지 맡고 있다

Status: ready-for-agent
Category: enhancement
Source: Standards 리뷰 — Divergent Change, Data Clumps (판단)

## 문제

`cli.py`(544줄)는 서로 무관한 이유로 바뀐다. 명령 parsing 외에 다음 일까지 한다.

- DB 조회: `indexed_repositories`, `accepted_digests`
- 측정: `timed_recommendation`
- 부하 질문 생성: `question_order`, `question_file`

`cmd_eval`(`cli.py:281-424`)은 함수 하나가 약 140줄이다. 또 `RunTrace`의 `seconds_*`와 `advise_prompt` 필드 5개를 `replace(score, ...)`로 하나씩 옮겨 담는다(`cli.py:366-374`). score가 `RunTrace`를 통째로 들고 있으면 된다.

## 완료 조건

- 평가 실행 로직은 `eval/` 아래로, 부하 질문 생성은 `loadtest/` 아래로 옮긴다. 계층 규칙(`test_layering.py`)은 지킨다.
- `CaseScore`와 `RunTrace` 사이의 필드 복사를 없앤다.
- 기존 테스트가 통과한다.

## Agent Brief

**Category:** enhancement
**Summary:** `cmd_eval`을 작은 함수로 나누고, 시간 기록을 `CaseScore`로 필드마다 복사하는 코드를 없앤다.

**Current behavior:**
CLI의 `eval` 명령 함수 하나가 약 140줄이다. 문항 거르기, 실행, 채점, meta 작성, report 저장을 모두 한다. 문항마다 측정한 `RunTrace`(`seconds_total`, `seconds_embedding`, `seconds_plan`, `seconds_advise`, `advise_prompt`)는 `dataclasses.replace`로 `CaseScore`에 필드 하나씩 복사된다.

계층 규칙상 stage를 조합하는 일은 `cli`만 할 수 있다. 그래서 평가 실행 로직을 `eval/`로, 부하 질문 생성을 `loadtest/`로 옮기는 방안은 이 issue에서 하지 않는다.

**Desired behavior:**
- 시간 기록 type(stage를 import하지 않는 순수 dataclass)을 `whatfrom.eval` 쪽에 정의하고, `CaseScore`가 이 type을 필드 하나로 갖는다. CLI의 측정 코드가 이 type을 채운다.
- 결과 JSON과 report 출력의 key와 형식은 지금 그대로 유지한다. 기존 `eval/results/` 파일과 계속 비교할 수 있어야 한다.
- `cmd_eval`을 단계별 함수로 나눈다. 단계는 문항 선택, 문항 하나 실행, meta 작성 정도다. 이 함수들은 `cli` 안에 둔다.

**Acceptance criteria:**
- [ ] `seconds_*`와 `advise_prompt`를 필드 단위로 복사하는 코드가 없다.
- [ ] 같은 입력이면 report와 결과 JSON의 key와 형식이 변경 전과 같다. 기존 report 테스트에서 `CaseScore`를 생성하는 부분(`make_score` 등)은 새 시간 기록 객체를 쓰도록 고쳐도 된다. 출력 assertion은 수정 없이 통과해야 한다.
- [ ] 이전 keyword 인자를 받는 호환 생성자를 두지 않는다.
- [ ] `eval` 명령 함수가 단계별 함수 호출로 읽힌다(대략 40줄 이하).
- [ ] 계층 테스트와 전체 테스트, `make lint`가 통과한다.

**Out of scope:**
- 최상위 조합 module을 새로 만드는 것.
- 부하 질문 생성(`question_order`, `question_file`)의 위치 이동.
- 채점 규칙 변경.
- `cli.py`를 고치는 issue 11, 12, 13과는 순서대로 작업한다.
