# V1 공통 골격

- Status: ready-for-agent
- roadmap: `docs/roadmap.md` Phase v2 V1
- 결정: `docs/adr/0003-judge-candidates-instead-of-recommending.md`
- 설계: `docs/design.md` §2, §7(근거), §8

## Problem Statement

`/recommend`는 추천 1개, 이유, 대안, Dockerfile 초안을 돌려준다. 주 사용자인 LLM agent에게는 두 가지가 맞지 않는다.

- Dockerfile 초안은 질문 한두 문장으로 추측해 쓴 것이다. agent는 프로젝트 파일을 보고 더 정확한 Dockerfile을 쓸 수 있는데, 추측한 초안이 오히려 방해가 된다.
- 추천 이유는 LLM이 쓴 문단일 뿐이다. 이유가 정말 공식 문서에 근거하는지 받는 쪽이 확인할 방법이 없다. 근거 문서는 후보마다 같은 섹션 본문이 반복해 들어 있어, 이유의 어느 부분이 어느 문서에서 왔는지도 알 수 없다.

ADR 0003은 Dockerfile 생성을 빼고, 두 번째 LLM 호출의 근거 인용을 결정론적으로 검증하기로 했다.
두 번째 LLM 호출을 후보 비교표로 할지, 인용을 붙인 단일 선택으로 둘지는 M3에서 정한다. V1은 두 안이 함께 쓸 골격을 만든다.

## Solution

`/recommend`가 Dockerfile 대신, 후보마다 고정 참조(`image@digest`)와 번호가 붙은 근거, 그리고 검증된 근거 인용을 돌려준다.

- 근거는 응답 최상위에 번호를 붙여 한 번만 담는다. 후보는 그 번호로 자기 근거를 가리킨다.
- 두 번째 LLM 호출은 지금처럼 후보 하나를 고르고 이유를 쓰되, 이유를 뒷받침하는 근거 인용(근거 번호와 글자 그대로의 문장)을 함께 낸다.
- 서버는 인용마다 그 요청에서 넘긴 근거 본문 안에 글자 그대로 있는지 검증하고, 결과를 응답에 담는다. 검증에 실패한 인용이 있어도 추천은 버리지 않는다.
- agent는 고정 참조를 Dockerfile의 `FROM`에 그대로 쓰고, 검증된 인용으로 추천의 근거를 확인한다.

이 구조는 M3의 "인용을 붙인 단일 선택" 안의 골격이다. 후보 비교표 안은 M3에서 같은 근거 번호와 인용 검증 위에 만든다.

## User Stories

1. LLM agent로서, 후보마다 `image@digest` 고정 참조를 받고 싶다. 그래야 digest를 따로 찾지 않고 고정된 `FROM` 줄을 쓸 수 있다.
2. LLM agent로서, digest를 수집하지 못한 후보는 그렇다고 명시해 받고 싶다. 그래야 없는 값으로 고정하지 않는다.
3. LLM agent로서, 응답에 Dockerfile 초안이 없기를 원한다. 그래야 추측한 진입점이나 의존성 파일이 프로젝트를 보고 쓰는 내 Dockerfile에 섞이지 않는다.
4. LLM agent로서, 근거 섹션을 번호, repository, 섹션 제목, 출처 URL, 본문과 함께 한 번씩만 받고 싶다. 그래야 중복 없이 근거를 읽을 수 있다.
5. LLM agent로서, 후보마다 자기 근거의 번호 목록을 받고 싶다. 그래야 어느 문서가 어느 이미지에 관한 것인지 안다.
6. LLM agent로서, 추천에 근거 번호와 글자 그대로의 문장으로 된 근거 인용이 붙기를 원한다. 그래야 이유를 문서와 직접 대조할 수 있다.
7. LLM agent로서, 근거 인용마다 서버가 검증했는지 알고 싶다. 그래야 검증된 인용은 믿고 아닌 것은 무시할 수 있다.
8. LLM agent로서, 검증에 실패한 인용은 실패 이유를 알고 싶다. 그래야 근거 번호를 잘못 단 것인지 문장을 바꿔 쓴 것인지 구분할 수 있다.
9. LLM agent로서, 인용이 모두 실패한 추천도 그 사실을 표시한 채 받고 싶다. 그래야 인용 실수 때문에 유효한 이미지 선택을 잃지 않는다.
10. LLM agent로서, 인용은 서버가 실제로 LLM에 넘긴 근거 본문 안에 있을 때만 통과하기를 원한다. 그래야 호출과 검증 사이에 다시 색인해도 판정이 바뀌지 않는다.
11. LLM agent로서, 인용과 문서 사이의 공백 차이는 무시되기를 원한다. 그래야 README의 줄바꿈 때문에 정확한 인용이 떨어지지 않는다.
12. LLM agent로서, 빈 인용은 검증에 실패하기를 원한다. 그래야 빈 문자열이 어떤 문서에든 일치하는 것으로 통과하지 않는다.
13. LLM agent로서, 추천이나 대안 이미지가 아닌 repository의 근거를 인용하면 실패하기를 원한다. 그래야 python 추천을 node 문서로 뒷받침하지 않는다.
14. LLM agent로서, 추천이 버려지거나 LLM 호출이 실패해도 근거 목록과 후보를 받고 싶다. 그래야 저하된 답에서도 사실과 문서를 얻는다.
15. LLM agent로서, 지금의 저하 알림이 그대로 남기를 원한다. 그래야 답이 왜 저하됐는지 안다.
16. API를 직접 부르는 사람으로서, agent와 같은 응답 형식을 받고 싶다. 그래야 익힐 계약이 하나다.
17. 유지보수자로서, LLM이 응답과 같은 번호로 근거를 보기를 원한다. 그래야 인용한 번호가 양쪽에서 같은 섹션을 뜻한다.
18. 유지보수자로서, LLM 출력 schema가 근거 인용 목록을 required로 두기를 원한다. 그래야 strict json_schema 서버가 받아들이고 모델이 항상 그 필드를 채운다.
19. 유지보수자로서, Dockerfile 검증과 digest 고정 코드를 지우고 싶다. 그래야 없어진 기능의 코드가 남지 않는다.
20. 유지보수자로서, 인용 검증이 LLM도 DB도 쓰지 않는 결정론적 함수이기를 원한다. 그래야 모든 경우를 싸게 테스트할 수 있다.
21. 유지보수자로서, 환각 테스트가 인용을 지어내는 fake LLM을 다루기를 원한다. 그래야 "LLM은 인용을 지어내지 않는다"는 불변식을 CI가 고정한다.
22. 유지보수자로서, eval 결과 파일에 추천의 근거 인용과 검증 결과가 남기를 원한다. 그래야 V2가 저장된 결과로 인용 지표를 만들 수 있다.
23. 유지보수자로서, fake provider로 `make eval`이 계속 돌기를 원한다. 그래야 변경 내내 CI와 측정 도구가 멀쩡하다.
24. 부하 측정을 돌리는 유지보수자로서, 모의 LLM 서버가 새 schema로 답하기를 원한다. 그래야 부하 측정이 같은 경로를 계속 잰다.
25. 유지보수자로서, README가 Dockerfile 규칙 대신 새 응답과 인용 규칙을 설명하기를 원한다. 그래야 문서가 API와 맞는다.

## Implementation Decisions

### 응답 계약

- 응답 최상위에 근거 목록을 둔다. 근거마다 번호, repository, 섹션 제목, 본문, 출처 URL이 있다. 번호는 한 요청 안에서만 쓰고 1부터 매긴다.
- 근거는 (repository, 섹션 제목)으로 한 번만 담는다. 지금 추천 단계 prompt가 쓰는 중복 제거와 같은 규칙이다. 순서는 prompt에 나오는 순서와 같다.
- 후보는 근거 본문을 직접 담지 않고 자기 근거의 번호 목록을 담는다.
- 후보마다 고정 참조 `repository:tag@digest`를 담는다. digest를 수집하지 못한 후보는 고정 참조가 없다(null).
- 추천에서 Dockerfile 필드를 지운다. 추천은 이미지, 이유, 대안, 근거 인용을 담는다.
- 응답의 근거 인용마다 근거 번호, 인용 문장, 검증 통과 여부, 실패 이유가 있다. LLM이 채우는 schema에는 검증 결과가 없다. 검증 결과는 서버가 붙인다.
- 경로는 `/recommend` 그대로다. 외부 사용자가 없어 version을 올리지 않는다.

### 두 번째 LLM 호출

- 출력 schema는 이미지, 이유, 대안, 근거 인용 목록이다. 근거 인용은 근거 번호와 인용 문장이다. strict json_schema를 위해 모든 필드를 required로 둔다(지금 schema 생성 규칙 그대로).
- prompt는 근거를 응답과 같은 번호로 보여 준다. 인용은 근거 본문에서 문장을 글자 그대로 복사하라고 지시하고, 이유의 주장마다 인용을 붙이게 한다. 인용 수의 하한은 두지 않는다.
- Dockerfile 지시를 prompt에서 지운다.

### 인용 검증

결정론적 함수다. LLM과 DB를 쓰지 않는다. 입력은 근거 인용, 그 요청에서 넘긴 번호 붙은 근거 목록, 인용이 뒷받침할 수 있는 repository 집합이다.

- 근거 번호가 그 요청의 근거 목록에 없으면 실패한다.
- 인용 문장이 비어 있거나 공백뿐이면 실패한다.
- 인용 문장과 근거 본문의 연속 공백(줄바꿈 포함)을 공백 하나로 바꾼 뒤, 인용이 본문의 부분 문자열이 아니면 실패한다. 대소문자는 구분한다.
- 근거의 repository가 추천 이미지와 검증을 통과한 대안의 repository가 아니면 실패한다.
- 실패 이유는 위 네 가지를 구분할 수 있게 남긴다.

추천 이미지와 대안의 실재성 검증은 지금 규칙 그대로다. 추천 이미지가 후보가 아니거나 DB에 없으면 추천을 버리고, 실재하지 않는 대안은 떼어 낸다. 인용 검증은 그 다음에 돈다.
인용이 하나도 통과하지 못해도 추천은 버리지 않는다. 응답의 인용마다 실패가 표시되고, 알림에 검증에 실패한 인용 수를 적는다.

### 지우는 것

- Dockerfile의 `FROM` 고정(digest pinning)과 그 module.
- Dockerfile 이미지 참조 검증과, 검증에 걸린 Dockerfile을 비우는 API 처리.
- README의 Dockerfile 관련 규칙.

### 함께 바꾸는 것

- eval 결과 JSON은 문항마다 Dockerfile 대신 추천의 근거 인용과 검증 결과를 남긴다. 새 지표는 V2에서 만든다.
- 부하 측정용 모의 LLM은 새 schema로 답한다. 근거 인용은 빈 목록이다.
- `eval/experiments/` 아래 끝난 실험의 도구와 그 테스트는 기록이다. 새 schema 때문에 테스트가 깨지면 fixture만 고치고 실험은 다시 돌리지 않는다.
- 단계적 저하 사다리(설계 문서 §8)는 그대로다. 추천이 없는 응답에도 후보와 근거 목록을 담는다.

## Testing Decisions

좋은 테스트는 외부 동작만 본다. 응답 JSON과 함수의 반환값을 확인하고, 내부 자료 구조나 호출 순서는 확인하지 않는다.

- **`/recommend` API (주 seam).** 테스트 DB, fake embedder, fake LLM으로 앱을 띄우고 응답을 본다. 지금 API 테스트와 같은 방식이다.
  - 응답에 Dockerfile 필드가 없다.
  - 후보마다 고정 참조가 있고, digest가 없는 후보는 null이다.
  - 근거 목록에 번호가 붙고 중복이 없으며, 후보의 근거 번호가 그 목록을 가리킨다.
  - fake LLM이 근거에 있는 문장을 인용하면 검증 통과, 지어낸 문장이나 없는 번호를 인용하면 실패와 그 이유가 담긴다. 추천은 남는다.
  - LLM 실패, 추천 폐기, 임베딩 실패 같은 저하 경로에서도 후보와 근거 목록이 담긴다.
  - 기존 환각 테스트(없는 이미지 추천, 실재하지 않는 대안)는 그대로 통과한다.
- **인용 검증 함수 (보조 seam).** 경우가 많아 함수 단위로 테이블 주도 테스트를 쓴다. 지금 verify 테스트와 같은 방식이다. 통과, 공백 차이, 대소문자 차이, 빈 인용, 공백뿐인 인용, 없는 근거 번호, 다른 repository의 근거, 대안 repository의 근거를 다룬다.
- **두 번째 LLM 호출의 prompt와 schema.** 지금 advisor와 llm 테스트처럼, prompt에 응답과 같은 근거 번호가 나오고 Dockerfile 지시가 없는지, schema가 근거 인용을 required로 두는지 본다.
- **eval runner.** 지금 CLI eval 테스트처럼 fake provider로 돌려, 결과 JSON에 근거 인용과 검증 결과가 남는지 본다.
- **모의 LLM.** 지금 모의 LLM 테스트처럼 새 schema로 답하는지 본다.

## Out of Scope

- 후보 비교표, 판정, 세 등급 순위. M3에서 비교할 안이다.
- 구조화 힌트와 판단 요구 추출(V4).
- v2 평가 지표와 판단 요구 라벨(V2).
- 검색 보강과 upstream 문서 색인(V5).
- 인용이 이유를 실제로 뒷받침하는지의 검사. 결정론적 검증은 인용의 진위까지만 본다(설계 문서 §2).
- 검증에 실패한 인용을 이유로 다시 LLM을 부르는 것(설계 문서 §8).
- MCP server(V6).

## Further Notes

- 근거 번호와 인용 검증은 M3의 두 안이 그대로 쓴다. 후보 비교표 안에서는 인용이 칸마다 붙고, repository 규칙이 "그 후보의 repository"로 좁아진다.
- 인용 검증 실패율은 V2의 인용 검증 통과율 지표가 된다. V1에서는 결과 JSON에 기록만 한다.
- 응답 형식이 바뀌므로 README의 응답 예시와 검증 원칙 절을 고친다.
