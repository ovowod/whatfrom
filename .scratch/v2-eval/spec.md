# V2 평가 v2, 판단 요구 라벨, 대조군

- Status: ready-for-agent
- roadmap: `docs/roadmap.md` Phase v2 V2
- 결정: `docs/adr/0003-judge-candidates-instead-of-recommending.md`
- 설계: `docs/design.md` §10, Review Log

## Problem Statement

M3는 후보 비교표와 인용을 붙인 단일 선택을 같은 입력으로 비교해 두 번째 LLM 호출의 모양을 정한다. 지금의 평가로는 그 비교를 할 수 없다.

- 입력을 고정할 방법이 이전 실행의 검색 조건(`--plans`)뿐이다. 그 조건은 조건 추출 단계가 낸 것이라 추출 품질이 섞이고, 판단 요구는 아예 없다.
- golden set에 판단 요구가 없다. 후보 비교표 안은 판정할 요구가 있어야 돌릴 수 있다.
- 추천 정확도만 있고, 그것이 LLM의 판단 덕인지 검색 순위 덕인지 가를 대조군이 없다. M1-b에서 검색 1위만 골라도 약 26/40이 맞았다.
- 명시적 오답이 실제 후보 목록에 나오는 문항이 16/40이다. 라벨은 38문항에 있지만 검색이 돌려주는 태그와 어긋나, 오답 적발률의 분모가 작다.
- 인용이 진술을 실제로 뒷받침하는지 잴 방법이 없다. LLM judge는 다시 사람 라벨과 대조해야 해서 쓰지 않기로 했다(F16, design §10).
- V1의 인용 경로는 실제 LLM으로 부른 적이 없다.

## Solution

평가를 v2 지표로 넓히고, M3와 V3가 쓸 고정 입력과 측정 도구를 만든다.

- **라벨 고정 입력**: eval이 검색 조건으로 golden set의 `expected_plan`과 `requires_repositories`를 쓴다. 조건 추출 단계를 부르지 않는다. 추천 단계를 부르는 실행과 부르지 않는 실행을 모두 지원한다.
- **검색 1위 대조군**: 판정 없이 검색 1위 후보를 추천으로 본 추천 정확도다. 무작위 선택 대조군처럼 후보가 있는 모든 실행에서 함께 낸다.
- **v2 지표**: 오답 적발률, 오판정률, 인용 검증 통과율을 더한다. 판정이 없는 실행에서 오답 적발률과 오판정률은 미측정이다.
- **판단 요구 라벨**: golden set 문항마다 `requirements`(짧은 영어 문장 목록, 빈 목록 허용)를 넣는다.
- **명시적 오답 보강**: 라벨 고정 입력의 후보 중 필수 요구를 어긴다고 문서가 말하는 태그를 reject에 더한다.
- **인용 뒷받침 표본 도구**: 결과 파일에서 (진술, 인용) 쌍 표본을 YAML로 뽑고, 사람이 채운 YAML로 인용 뒷받침률과 합격 여부를 낸다.
- **첫 실측**: 라벨 고정 입력으로 검색 1위 대조군을 재고, luna-none으로 V1의 인용 경로를 한 번 돌려 표본 도구까지 관통시킨다. 결과를 README에 기록한다.

## User Stories

1. 평가를 돌리는 개발자로서, 조건 추출 단계 없이 golden set 라벨을 검색 조건으로 쓰고 싶다. 그래야 두 번째 LLM 호출만 따로 잴 수 있다.
2. 평가를 돌리는 개발자로서, 라벨 고정 입력의 후보가 운영 경로와 같은 검색(조건 필터 포함)으로 나오기를 원한다. 그래야 그 결과가 실제 응답의 후보와 같은 것을 잰다.
3. 평가를 돌리는 개발자로서, 라벨 고정 입력에서 추천 단계를 부르지 않고도 후보를 얻고 싶다. 그래야 LLM 비용 없이 대조군과 검색 지표를 잰다.
4. 평가를 돌리는 개발자로서, 라벨 고정 입력으로 돌린 결과의 meta에 그 사실이 남기를 원한다. 그래야 다른 입력으로 잰 결과와 섞어 비교하지 않는다.
5. 평가를 돌리는 개발자로서, 라벨 고정 입력의 실행이 조건 추출 지표를 내지 않기를 원한다. 그래야 부르지 않은 단계의 점수를 읽지 않는다.
6. 평가를 돌리는 개발자로서, 검색 1위 대조군을 추천 정확도 옆에서 보고 싶다. 그래야 추천이 검색 순위보다 나은지 안다.
7. 평가를 돌리는 개발자로서, 검색 1위 대조군이 추천 정확도와 같은 허용 규칙(digest 인정 포함)으로 채점되기를 원한다. 그래야 두 값을 같은 자로 비교한다.
8. 평가를 돌리는 개발자로서, 후보가 없는 문항은 검색 1위 대조군에서 오답으로 세기를 원한다. 그래야 분모가 추천 정확도와 같다.
9. 평가를 돌리는 개발자로서, 검색 1위 대조군이 결과 JSON에도 문항별로 남기를 원한다. 그래야 어느 문항에서 LLM이 순위를 뒤집었는지 본다.
10. 평가를 돌리는 개발자로서, 인용 검증 통과율을 보고 싶다. 그래야 LLM이 근거 본문을 글자 그대로 옮기는지 안다.
11. 평가를 돌리는 개발자로서, 인용이 하나도 없는 실행에서 인용 검증 통과율이 0%가 아니라 미측정으로 나오기를 원한다. 그래야 인용이 없는 것과 모두 틀린 것을 구분한다.
12. 평가를 돌리는 개발자로서, 오답 적발률을 보고 싶다. 그래야 명시적 오답 후보가 불만족 판정을 받는지 안다.
13. 평가를 돌리는 개발자로서, 오판정률을 보고 싶다. 그래야 허용 정답 후보가 억울하게 불만족 판정을 받는지 안다.
14. 평가를 돌리는 개발자로서, 판정이 없는 실행에서 오답 적발률과 오판정률이 미측정으로 나오기를 원한다. 그래야 단일 선택 안과 V2 실행을 0%로 오해하지 않는다.
15. 평가를 돌리는 개발자로서, 명시적 오답이 후보에 없는 문항은 오답 적발률의 분모에서 빠지기를 원한다. 그래야 적발할 기회가 없던 문항을 실패로 세지 않는다.
16. 라벨을 쓰는 개발자로서, golden set 문항마다 판단 요구 목록을 적고 싶다. 그래야 M3와 V3가 같은 요구로 판정을 잰다.
17. 라벨을 쓰는 개발자로서, 판단 요구가 없는 문항을 빈 목록으로 적고 싶다. 그래야 "아직 안 씀"과 "요구 없음"을 가른다.
18. 라벨을 쓰는 개발자로서, `requirements` 키가 없거나 빈 문장이 든 golden set을 loader가 거부하기를 원한다. 그래야 라벨 누락이 조용히 지나가지 않는다.
19. 라벨을 검토하는 사람으로서, 질문만 보고 쓴 판단 요구 초안을 받고 싶다. 그래야 라벨이 정답 목록에 맞춰 쓰이지 않는다.
20. 라벨을 검토하는 사람으로서, 초안 중 조건, 명시적 오답, 근거와 어긋나는 문항이 위에 표시된 표를 받고 싶다. 그래야 F16에서 놓쳤던 함정(빌드 stage 문항, 베이스에 이미 든 도구, 권장하지 않음과 위반의 혼동)을 먼저 본다.
21. 라벨을 검토하는 사람으로서, 필터로 거를 수 있는 요구나 후보끼리 견줘야 하는 선호가 판단 요구에 들어오지 않기를 원한다. 그래야 판정 단계가 후보 하나만 보고 판정할 수 있다.
22. 라벨을 검토하는 사람으로서, 라벨 고정 입력의 후보 중 accept에도 reject에도 없는 태그 목록과, 그중 필수 요구를 어긴다고 문서가 말하는 태그를 근거와 함께 받고 싶다. 그래야 reject 보강을 근거로 검토한다.
23. 라벨을 검토하는 사람으로서, 허용 정답이 바뀌지 않고, 라벨 보강으로 추천 정확도, 후보 포함률, 대조군이 바뀌면 그 변화가 기록되기를 원한다. 그래야 지난 결과와 비교할 때 라벨 탓인 차이를 가른다.
23-1. 라벨을 검토하는 사람으로서, 기존 reject 중 선호(예: 더 크다)를 근거로 한 태그가 빠지기를 원한다. 그래야 판정 단계가 잡을 수 없는 오답이 오답 적발률을 깎지 않는다.
24. 라벨을 검토하는 사람으로서, 보강 전후에 명시적 오답이 후보에 나오는 문항 수를 알고 싶다. 그래야 보강이 오답 적발률의 분모를 얼마나 늘렸는지 안다.
25. 인용을 채점하는 사람으로서, 결과 파일 여러 개에서 한 번에 표본을 뽑고 싶다. 그래야 M3의 두 안을 한 자리에서 채점한다.
26. 인용을 채점하는 사람으로서, 표본에서 설정과 안의 이름이 가려지기를 원한다. 그래야 어느 안의 인용인지 모르고 채점한다.
27. 인용을 채점하는 사람으로서, 표본 항목마다 진술, 그 진술이 가리키는 이미지, 인용 문장, 인용한 근거의 repository와 섹션 제목을 보고 싶다. 그래야 인용 문장만으로 진술이 성립하는지 판단하고, 다른 태그를 다룬 문장을 인용한 경우를 가린다.
28. 인용을 채점하는 사람으로서, 글자 그대로 검증에 실패한 인용은 표본에 없기를 원한다. 그래야 인용 검증 통과율이 이미 잡은 실패를 다시 보지 않는다.
29. 인용을 채점하는 사람으로서, 한 문항이 표본을 독차지하지 않기를 원한다(문항당 최대 2쌍). 그래야 인용이 많은 문항이 결과를 좌우하지 않는다.
30. 인용을 채점하는 사람으로서, 같은 seed로 다시 뽑으면 같은 표본이 나오기를 원한다. 그래야 채점을 재현하고 이어서 할 수 있다.
31. 인용을 채점하는 사람으로서, 편집기에서 `verdict: supported|unsupported|unclear`만 따옴표 없이 채우면 되기를 원한다. 그래야 도구 없이 중간에 멈췄다 이어서 채점한다.
32. 인용을 채점하는 사람으로서, 채운 표본에서 안마다 인용 뒷받침률, unclear 수, 채점하지 않은 항목 수, 합격 여부를 받고 싶다. 그래야 M3와 V3의 판정에 바로 쓴다.
33. 인용을 채점하는 사람으로서, 채점하지 않은 항목이 남아 있거나, 행이 빠지거나 복제되거나, 채점 칸 밖의 내용이 바뀌었으면 합격 여부를 내지 않기를 원한다. 그래야 덜 채우거나 손상된 표본으로 합격을 선언하지 않는다.
33-1. 인용을 채점하는 사람으로서, unclear가 너무 많거나 채점할 수 있는 쌍이 없으면 합격 여부가 보류되기를 원한다. 그래야 unclear를 분모에서 빼는 규칙이 합격을 부풀리지 않는다.
34. 인용을 채점하는 사람으로서, 표본의 쌍이 50개보다 적으면 그 사실을 알고 싶다. 그래야 인용이 적은 안의 합격 판정을 따로 본다.
35. 인용을 채점하는 사람으로서, 표본 파일과 채점 결과를 실험 기록 디렉터리에 그대로 넣고 싶다. 그래야 판정 근거가 repository에 남는다.
36. 프로젝트 유지자로서, README에서 라벨 고정 입력으로 잰 검색 1위 대조군과 luna-none 실행의 인용 지표를 보고 싶다. 그래야 M3 전의 출발점을 안다.
37. 프로젝트 유지자로서, luna-none 실행 결과가 모델 선택 근거가 아니라고 기록되기를 원한다. 그래야 ADR 0003과 어긋나는 결론을 끌어내지 않는다.
38. 프로젝트 유지자로서, V1의 인용 경로가 실제 LLM 출력에서 깨지면(strict schema 거부, 인용 0개, 표본 도구 오류) V2 안에서 알고 싶다. 그래야 M3에서 두 안을 함께 돌리다 찾지 않는다.

## Implementation Decisions

**라벨 고정 입력**

- eval에 라벨 고정 입력 option을 더한다. 문항마다 `expected_plan`의 필드와 `requires_repositories`의 repository로 검색 조건을 만들고, 조건 추출 단계 자리에 끼운다. `--plans`의 고정 provider와 같은 방식이다.
- 40문항 모두 repository가 하나다. repository가 둘 이상인 문항이 생기면 loader나 eval이 멈춘다. 지금 그런 문항을 처리할 규칙을 만들지 않는다.
- 추천 단계를 부르는 방식과 부르지 않는 방식을 둘 다 둔다. 부르지 않는 방식은 추천 단계를 실패로 다루는 provider를 끼워 기존 저하 경로로 후보와 근거를 얻는다. LLM 호출은 0회다.
- 기존 `--retrieval-only`(검색 조건 없이 벡터 검색)는 그대로 둔다. 라벨 고정 입력과의 조합 방식(새 mode 또는 option 조합)은 구현에서 정하되, 결과 meta의 mode 이름으로 두 실행을 구분할 수 있어야 한다.
- 결과 meta에 라벨 고정 입력임을 남긴다. 조건 추출 지표는 내지 않는다.
- `--plans`는 바꾸지 않는다. golden set이 바뀌면 hash 검사로 이전 결과를 못 쓰게 되는 것도 그대로다.

**검색 1위 대조군**

- 문항마다 응답 후보 목록의 첫 후보가 허용 집합에 드는지를 추천 정확도와 같은 함수(digest 인정 포함)로 채점해 문항 점수에 담는다. 후보가 없으면 오답이다.
- 집계는 기존 대조군(고정답, 무작위 선택)과 같은 자리에 낸다. 후보가 있는 모든 실행에서 낸다.
- 후보 목록의 순서는 운영 경로가 돌려준 순서 그대로다. eval이 다시 정렬하지 않는다.

**v2 지표**

- 인용 검증 통과율: 응답의 주장들에 붙은 인용 전체를 분모로, 검증을 통과한 인용을 분자로 센다. 분모가 0이면 미측정이다.
- 오답 적발률과 오판정률: design §10의 정의대로 후보 단위로 센다. 오답 적발률의 분모는 후보로 나온 명시적 오답, 오판정률의 분모는 후보로 나온 허용 정답이다.
  지금 응답에는 판정이 없으므로 집계 함수는 후보별 "불만족 판정을 하나 이상 받았는가"를 입력으로 받고, 판정이 없는 실행은 미측정으로 낸다. 판정을 응답에서 꺼내는 부분은 V3가 채운다.
- 명시적 오답이 후보에 나온 문항 수를 결과에 기록한다(라벨 보강 전후 비교용).
- 미측정은 지금 `Metric.ratio`가 분모 0을 다루는 규칙을 따른다.

**golden set**

- 문항 스키마에 `requirements: list[str]`을 더한다. 키는 필수이고 빈 목록을 허용한다(`expected_plan`과 같은 원칙). 빈 문자열이나 공백만 있는 문장은 거부한다.
- 판단 요구는 짧은 영어 문장 하나로 쓰고, 후보 하나만 보고 판정할 수 있는 요구만 쓴다. 필터로 거르는 요구(아키텍처, 버전, 배포판, 크기 상한)와 후보끼리 견줘야 하는 선호는 쓰지 않는다. 이 기준은 golden set 머리 주석에 적는다.
- reject 보강은 태그 단위로 한다. 라벨 원칙(존재를 확인한 태그, 근거 URL, 필수 요구 위반만)을 그대로 따른다. 허용 정답은 고치지 않는다.
- accept 태그와 digest가 같은 후보는 reject에 넣지 않는다. 같은 이미지가 요구를 만족하면서 어길 수는 없다. 태그가 다른 이미지로 옮겨 갈 수 있다는 것 자체가 위반 사유이면(`postgres:latest`처럼) 근거를 적고 넣는다. 채점은 reject를 digest 일치보다 먼저 보므로, 이런 태그는 정확도를 바꾼다.
- 기존 reject도 검토한다. 선호(크기가 더 크다 등)를 근거로 한 태그는 빼고 그 이유를 근거에 적는다. 크기를 묻는 문항(`python-size-first`, `node-size-first`, `redis-cache-sidecar`, `nginx-static-spa`, `debian-slim-runtime` 등)이 대상이다. 빠진 태그는 명시적 오답 경보를 잃는다.
- 스키마가 바뀌므로 golden set `version`을 2로 올린다. `verified_on`은 모든 근거를 다시 열지 않으므로 그대로 두고, 이번에 확인한 범위를 머리 주석에 적는다.

**라벨 작업 절차**

- subagent가 질문만 보고 판단 요구 초안을 쓴다. accept, reject, rationale, conditions는 넘기지 않는다.
- 초안을 문항의 conditions, reject, rationale과 대조해 어긋나는 문항을 표시한다. 표시 기준: 필터로 거를 수 있는 요구, 선호, 베이스 이미지에 이미 있는 것을 요구함, reject를 설명하는 요구가 없음, 빌드 stage 문항을 런타임 요구로 씀.
- reject 보강 후보는 라벨 고정 입력(추천 단계 미호출) 실행의 후보에서 뽑는다.
- 보강 전후에 추천 정확도(같은 출력을 다시 채점한 값), 후보 포함률, 검색 1위 대조군, 명시적 오답이 후보에 나온 문항 수를 기록한다.
- 두 표를 사람이 40문항 모두 검토한 뒤 golden set에 반영한다.

**인용 뒷받침 표본 도구**

- `whatfrom eval` 아래 하위 명령 두 개(표본 생성, 채점 집계)로 둔다. 별도 패키지 계층을 만들지 않고 `whatfrom.eval` 안에 둔다(계층 규칙: `whatfrom.eval`은 자기 자신과 `whatfrom.core`만 import한다).
- 결과 JSON의 문항 기록에 번호가 붙은 근거 목록(번호, repository, 섹션 제목, 출처 URL)을 저장한다. 본문은 크기 때문에 넣지 않는다. 표본 도구는 이 목록으로 인용의 근거 정보를 찾는다.
- 단위는 검증을 통과한 (진술, 인용) 쌍이다. 지금의 진술은 단일 선택의 주장 문장이고, 그 주장이 가리키는 이미지는 추천 이미지다. 후보 비교표의 판정 칸("후보 X가 요구 R을 만족/불만족")은 M3에서 같은 쌍 형식으로 더한다.
- 표본 생성: 결과 파일 여러 개를 받아 파일(안)마다 최대 50쌍을 뽑는다. 문항당 최대 2쌍, seed는 인자로 받고 기본값을 고정한다. 항목 순서를 섞고 익명 id를 붙여 설정 이름을 가린다.
- 표본 YAML 항목: 익명 id, 진술, 이미지, 인용 문장, 근거의 repository와 섹션 제목, `verdict`(비어 있음). 값은 `supported`, `unsupported`, `unclear`다. YAML이 `yes`와 `no`를 bool로 읽으므로 이 어휘를 쓴다.
- 익명 id와 원래 (결과 파일, 문항, 주장, 인용)의 대응, 그리고 항목마다 `verdict`를 뺀 내용의 hash를 별도 key 파일에 둔다. 채점하는 사람은 key 파일을 열지 않는다.
- 채점 집계: 채운 표본과 key 파일을 읽어 안마다 뒷받침률(supported ÷ (supported + unsupported)), 채점 가능한 쌍 수(supported + unsupported), unclear 수, 비어 있는 항목 수, 표본 쌍 수를 낸다.
- 다음이면 합격 여부를 내지 않는다: 비어 있는 항목이 있음, 값이 세 어휘 밖임, id가 중복됨, 표본의 id 집합이 key 파일과 다름(빠진 행은 채점하지 않은 것으로 셈), `verdict` 밖의 내용이 hash와 다름.
- 채점 가능한 쌍이 0이면 뒷받침률은 미측정이다. unclear가 표본 쌍의 10%를 넘으면 합격 여부를 보류하고 그 사실을 표시한다.
- 합격선은 90%다(표본 50쌍이면 45/50). 표본이 50쌍보다 적으면 그 사실을 표시한다.

**첫 실측**

- 라벨 고정 입력, 추천 단계 미호출로 검색 1위 대조군과 검색 지표를 잰다. 라벨 보강 전후 모두 잰다.
- luna-none(`gpt-6-luna`, `reasoning_effort: none`)으로 라벨 고정 입력에서 추천 단계를 한 번 돌린다. 인용 검증 통과율을 기록하고, 그 결과로 표본을 뽑아 사람이 채점한다.
- 결과는 `eval/experiments/<날짜>-v2-first-run/`에 남기고 README에 요약한다. 모델 선택 근거가 아니라고 적는다.

## Testing Decisions

좋은 테스트는 외부 동작만 본다. CLI 출력, 결과 JSON, loader의 수락과 거부, 집계 함수의 반환값이다. 내부 함수 호출 순서나 provider 구현 세부는 보지 않는다.

- **`whatfrom eval` CLI**(높은 seam, `tests/test_cli_eval.py` 방식: fake embedder, fake provider, 테스트 DB)
  - 라벨 고정 입력이 조건 추출 단계를 부르지 않고, 검색 조건이 라벨과 같다.
  - 라벨 고정 입력, 추천 단계 미호출 실행이 LLM을 한 번도 부르지 않고 후보와 대조군을 낸다.
  - 결과 meta가 라벨 고정 입력을 기록하고, 조건 추출 지표가 없다.
  - 요약과 결과 JSON에 검색 1위 대조군, 인용 검증 통과율, 오답 적발률과 오판정률(미측정)이 나온다.
- **표본 도구**(같은 CLI seam. 입력은 fake provider로 실제 `whatfrom eval`을 돌려 나온 결과 파일이다)
  - 결과 JSON에 근거 목록(번호, repository, 섹션 제목, 출처 URL)이 저장된다.
  - 문항당 최대 2쌍, 파일마다 최대 50쌍, 검증 실패 인용 제외, 같은 seed면 같은 표본.
  - 표본 YAML에 설정 이름과 결과 파일 이름이 없다.
  - 채점 집계는 손으로 채운 YAML 텍스트를 그대로 읽는다: 세 어휘, 빈 값, `yes` 같은 잘못된 값.
  - unclear는 분모에서 빠진다. 채점 가능한 쌍 0은 미측정, unclear 10% 초과는 보류.
  - id 중복, 행 누락, key 파일과 다른 id, 채점 칸 밖 내용 변경은 합격 여부를 내지 않는다.
  - 50쌍 미만이면 표시한다. 합격선 경계(45/50 합격, 44/50 불합격).
- **golden set loader**(`tests/eval/test_goldenset.py`, `tests/eval/test_goldenset_file.py`)
  - `requirements` 키가 없으면 거부, 빈 목록은 수락, 빈 문장은 거부.
  - 실제 파일의 모든 문항이 `requirements`를 가진다. 모든 문항의 repository가 하나다.
- **집계 순수 함수**(`tests/eval/test_report.py`, `tests/eval/test_scoring.py`)
  - 검색 1위 대조군: digest 인정, 후보 없음은 오답.
  - 오답 적발률과 오판정률: 명시적 오답이 후보에 없는 문항은 분모에서 빠짐, 판정이 없으면 미측정.
  - 인용 검증 통과율: 인용 0개는 미측정.
- **계층 규칙**: `tests/test_layering.py`가 새 코드에도 그대로 통과한다.
- 라벨 작업(초안, 대조, 보강, 검토)은 코드가 아니어서 테스트하지 않는다. 산출물은 ticket의 검토 표다.

## Out of Scope

- 판정 단계와 후보 비교표 구현, 응답의 판정 계약(V3, M3).
- 판단 요구 추출과 구조화 힌트(V4). 판단 요구 추출 품질 지표도 V4에서 정한다.
- reject 태그와 판단 요구의 연결(오답 적발률을 "그 요구를 불만족"으로 엄격하게 하는 것). 필요해지면 M3 뒤에 더한다.
- reject를 태그 대신 규칙(변형 패턴)으로 바꾸는 것.
- 허용 정답 수정.
- LLM judge로 인용 뒷받침을 재는 것.
- 두 번째 LLM 호출의 모델 선택(M2). M3의 비교 기준(M3를 측정하기 전에 정함).
- 검색 보강(V5)과 repository를 정하지 못한 질문의 처리.

## Further Notes

- 오답 적발률과 오판정률은 V2에서 계산 코드와 테스트만 생긴다. 실제 값은 V3(또는 M3의 후보 비교표 안)부터 나온다.
- 표본 도구의 진술은 V2에서 주장 문장뿐이다. 판정 칸을 진술로 바꾸는 부분은 M3에서 더하되, 표본 YAML과 집계 형식은 바꾸지 않는다.
- luna-none은 M1-b에서 Dockerfile까지 쓰는 작업으로 고른 설정이다. 이번 실행은 V1 경로와 도구의 관통 확인이다.
- M1-b 실측(luna-none-r1): 검색 1위를 태그로만 대조하면 약 26/40, LLM 추천 37/40, 무작위 선택 대조군 기대값 약 58%, 명시적 오답이 후보에 나온 문항 16/40. 라벨 고정 입력에서는 후보가 달라지므로 다시 잰다.
