# M1-a 조건 추출 단계의 LLM 비교

- Status: ready-for-agent
- roadmap: `docs/roadmap.md` Phase 3 M1 (공통 규칙, M1-a)
- 근거: `docs/research/2026-10-03-m1-llm-candidates.md`

## Problem Statement

조건 추출 단계는 지금 kimi-k3로 돌고, `reasoning_effort`를 보내지 않아 reasoning 기본값 `max`가 적용된다.
이 단계에 더 빠른 모델을 써도 검색 조건의 정확도가 유지되는지 알 수 없다.

F14로 단계별 설정과 `make eval-plan`은 생겼지만, 모델마다 어떤 설정으로 몇 번 돌리고 무엇을 비교해 고르는지가 정해져 있지 않다.
공급자마다 structured output 처리와 token 보고 방식이 달라서, 그대로 돌리면 아래 문제가 생길 수 있다.

- schema 거부(400) 하나로 40문항이 모두 실패한다.
- 서로 다른 뜻의 token 수를 같은 비용 공식으로 계산한다.

## Solution

비교 대상 모델마다 조건 추출 단계만 평가해, 정확도 하한을 넘은 모델 중 p95 지연이 가장 낮은 모델을 고른다.

1. **사전 확인:** 모든 측정 설정을 한 번씩 호출해 schema 거부와 `usage` 형식을 먼저 확인한다. 이 호출이 첫 요청 지연도 흡수한다.
2. **측정:** 같은 날 kimi-k3 기준선부터 차례로 돌린다. 기준선은 전체 평가로, 나머지는 `eval --plan-only`로 잰다.
3. **집계:** 결과 JSON을 검증한 뒤 모아 정확도, 지연, 재시도, token, 비용을 한 표로 만든다.
4. **기록:** 결론과 근거를 `eval/experiments/<측정일>-plan-llm-comparison/`에 남기고 roadmap을 갱신한다.

kimi-k3를 유지하는 결론도 될 수 있다.

## User Stories

1. 개발자로서, 비교 대상 모델마다 정해진 설정 하나로 측정하고 싶다. 그래야 결과가 어떤 reasoning 수준에서 나온 것인지 분명하다.
2. 개발자로서, 측정 전에 모델마다 한 번 호출해 schema 거부를 확인하고 싶다. 그래야 유료 평가 40문항을 400으로 날리지 않는다.
3. 개발자로서, 사전 확인에서 원본 `usage`를 보고 싶다. 그래야 Gemini의 token 보고 방식을 문서 없이도 확정할 수 있다.
4. 개발자로서, 사전 확인 호출이 첫 schema 처리 지연을 흡수하게 하고 싶다. 그래야 첫 문항이 p95를 끌어올리지 않는다.
5. 개발자로서, kimi-k3 기준선을 운영 설정(`max`)의 전체 평가로 같은 날 다시 재고 싶다. 그래야 정확도 하한이 지금 운영 품질을 기준으로 하고, M1-b가 그 결과의 검색 조건을 고정해 쓸 수 있다.
6. 개발자로서, kimi-k3도 `low`로 재서 후보에 넣고 싶다. 그래야 공급자를 바꾸지 않는 선택지도 공정하게 비교된다.
7. 개발자로서, 공급자별 API 키를 환경 변수로 주고 측정을 명령 하나로 돌리고 싶다. 그래야 키를 `.env`에 번갈아 넣지 않는다.
8. 개발자로서, API 키가 결과 파일이나 로그에 남지 않기를 바란다.
9. 개발자로서, 모델마다 repository 추출 일치율과 조건 추출 일치율을 기준선과 나란히 보고 싶다.
10. 개발자로서, 모델마다 조건 추출 단계 소요 시간의 p50과 p95를 보고 싶다. 지금 report는 중앙값과 최댓값만 보여 준다.
11. 개발자로서, 재시도가 섞인 문항 수를 보고 싶다. 그래야 그 모델의 지연을 믿을 수 있는지 판단한다.
12. 개발자로서, 실패한 호출 수와 실패 이유를 보고 싶다. 그래야 timeout이나 schema 위반이 정확도에 섞였는지 안다.
13. 개발자로서, 공급자별 규칙으로 보정한 출력 token과 40문항 비용을 보고 싶다. 그래야 grok의 reasoning token을 빠뜨리거나 OpenAI의 것을 두 번 세지 않는다.
14. 개발자로서, 정확도 하한 ±2문항 안에 든 모델만 한 번 더 돌리고 두 회차 평균으로 판정하고 싶다. 그래야 경계에 있는 모델을 한 번의 흔들림으로 판정하지 않는다.
15. 개발자로서, 모든 측정이 같은 문항과 같은 repository 목록을 받았는지 집계 전에 확인하고 싶다. 그래야 입력 차이를 모델 차이로 착각하지 않는다.
16. 개발자로서, fake provider나 다른 설정으로 돈 결과가 집계에 섞이면 집계가 멈추기를 바란다.
17. 개발자로서, 알 수 없는 비용은 "알 수 없음"으로 보고 싶다. 그래야 추정치로 모델을 고르지 않는다.
18. 개발자로서, 고르는 기준이 숫자로 정해져 있고 비교 순서와 무관하게 같은 답을 내기를 바란다. 그래야 결과를 본 뒤 기준을 바꾸고 싶어지지 않는다.
19. 개발자로서, 사전 확인에서 배제된 모델과 이유를 결과 문서에서 보고 싶다.
20. 개발자로서, 결과 JSON이 git에 남기를 바란다. `eval/results/`는 추적하지 않으므로 실험 폴더에 복사한다.
21. 개발자로서, 실험 README에 코드 commit, golden set hash, repository 목록, 모델별 설정, 측정 시각을 남기고 싶다. 그래야 나중에 같은 조건으로 다시 잴 수 있다.
22. 개발자로서, 측정이 끝나면 roadmap의 M1-a가 완료로 바뀌고 고른 모델이 적혀 있기를 바란다.
23. 개발자로서, M1-a 결론이 운영 설정을 바로 바꾸지 않기를 바란다. 두 단계 조합은 M1-b 완료 판정에서 확인한다.

## Implementation Decisions

### 측정 설정

| 이름 | base URL | 모델 | `WHATFROM_PLAN_LLM_EXTRA_BODY` | 키 환경 변수 |
| --- | --- | --- | --- | --- |
| kimi-max (기준선) | `https://api.moonshot.ai/v1` | `kimi-k3` | 비움 (운영과 같음) | `MOONSHOT_API_KEY` |
| kimi-low | `https://api.moonshot.ai/v1` | `kimi-k3` | `{"reasoning_effort": "low"}` | `MOONSHOT_API_KEY` |
| luna-none | `https://api.openai.com/v1` | `gpt-6-luna` | `{"reasoning_effort": "none"}` | `OPENAI_API_KEY` |
| grok-none | `https://api.x.ai/v1` | `grok-4.3` | `{"reasoning_effort": "none"}` | `XAI_API_KEY` |
| gemini-minimal | `https://generativelanguage.googleapis.com/v1beta/openai` | `gemini-3.5-flash-lite` | `{"extra_body": {"google": {"thinking_config": {"thinking_level": "minimal"}}}}` | `GEMINI_API_KEY` |

- Gemini는 기본값도 `minimal`이지만 명시한다. 결과 meta에 설정이 남는다.
- Gemini에 `reasoning_effort`는 쓰지 않는다. 3.5 Flash-Lite 대응이 문서에 없고, `thinking_level`과 같이 쓰면 안 된다.
- 추천 단계 설정은 건드리지 않는다. `--plan-only`는 추천 단계를 부르지 않는다.
- timeout(120초)과 재시도(429·5xx 최대 2회)는 운영과 같다.

### 실험 스크립트

M0처럼 실험 폴더에 스크립트를 둔다. 하는 일은 세 가지다.

- **사전 확인:** 측정 설정마다 golden set 첫 문항으로 조건 추출 단계를 한 번 부른다.
  - 평가와 같은 provider 코드로 부른다. 요청 본문을 따로 만들지 않는다.
  - provider에 주입하는 HTTP client로 원본 응답을 받아 `usage`를 그대로 출력한다.
  - 성공 여부, 실패 이유, 원본 `usage`를 사전 확인 기록 파일에 남긴다.
- **측정:** 측정 설정 하나를 받아, 그 설정을 `WHATFROM_PLAN_LLM_*` 환경 변수로 넣고 평가를 실행한다.
  - kimi-max는 전체 평가, 나머지는 `--plan-only`로 돌린다.
  - 항상 `--llm-provider openai_compatible`을 명시한다. 기본값이 `fake`라서 빠뜨리면 fake 응답이 측정된다.
  - LLM timeout은 운영값(120초)으로 고정해 넘긴다. 환경 변수에 다른 값이 있어도 덮어쓴다.
  - 공급자 키는 키 환경 변수에서 읽어 `WHATFROM_PLAN_LLM_API_KEY`로만 넘긴다.
  - 결과 JSON을 실험 폴더에 측정 설정 이름과 회차를 붙여 복사한다.
- **집계:** 실험 폴더의 결과 JSON을 검증한 뒤 비교 표를 만든다. 결과 JSON과 repository 목록 기록만 입력으로 받고 네트워크를 쓰지 않는다.

평가 코드(`whatfrom.eval`, `whatfrom.cli`)는 바꾸지 않는다. p95, token 보정, 비용은 집계에서 계산한다.

### 입력 고정

- 측정 시작 전과 마지막 측정 뒤에 DB의 repository 목록과 repository별 색인 문서 수를 기록한다. 두 기록이 다르면 이번 측정 전체가 무효다.
- 측정 동안 수집과 색인을 돌리지 않는다.
- 모든 결과는 golden set 40문항을 모두 측정해야 한다. 미측정 문항이 하나라도 있으면 측정을 멈추고 색인부터 맞춘다.

### 결과 검증

집계는 아래 중 하나라도 어긋나는 결과 파일이 있으면 표를 만들지 않고 멈춘다.

- 결과 meta의 `llm_provider`가 `openai_compatible`이 아니다.
- 결과 meta의 조건 추출 단계 base URL, 모델, 덧붙일 JSON이 측정 설정과 다르다.
- 모드가 다르다. kimi-max는 `full`, 나머지는 `plan-only`여야 한다.
- golden set hash가 다른 결과와 다르다.
- 측정한 문항 ID 집합이 golden set 40문항과 다르다.

### 사전 확인 규칙

- 모든 측정 설정의 사전 확인이 끝난 뒤에 측정을 시작한다. 기준선도 마찬가지다.
- **kimi-max 기준선은 반드시 있어야 한다.** 기준선 없이는 정확도 하한을 정할 수 없다. kimi-max의 사전 확인이나 측정이 끝내 실패하면 모델을 고르지 않고 M1-a를 미완료로 둔다.
- 실패는 두 가지로 나눈다.
  - **일시적 실패:** 429, 5xx, timeout, 연결 실패. 시간을 두고 사전 확인을 다시 한다. 같은 날 세 번 실패하면 영구적 실패로 본다.
  - **영구적 실패:** 그 밖의 4xx. 모델 ID 없음, 권한 없음, 지원하지 않는 parameter, schema 거부가 여기 해당한다.
- **schema 때문에 400이 나면** 코드에서 고친다.
  - `strict_json_schema`가 `"default": null`을 지운다. OpenAI 공식 SDK가 strict schema를 만들 때 하는 것과 같다.
  - 모든 공급자에 같이 적용하고, 모든 측정 설정의 사전 확인을 다시 한다.
  - 기준선은 고친 뒤에 재므로 모든 모델이 같은 schema를 받는다.
- schema와 무관한 영구적 실패면 그 모델을 배제하고 이유를 기록한다. kimi-max는 배제하지 않고 위 규칙대로 M1-a를 미완료로 둔다.
- 사전 확인 호출은 결과 집계에 넣지 않는다.

### 측정 규칙

- 모든 측정을 같은 날 한다. 순서는 kimi-max, kimi-low, luna-none, grok-none, gemini-minimal이다.
- 측정 설정마다 1회 돌린다.
- 두 일치율 중 하나라도 하한 ±2문항 안에 들면 한 번 더 돌린다. 기준선은 하한을 정하는 쪽이라 다시 돌리지 않는다.

**회차 합치기**

| 지표 | 한 번 돈 설정 | 두 번 이상 돈 설정 |
| --- | --- | --- |
| 일치율 (하한 판정, 동점 판정) | 그 회차 값 | 정확도 측정 회차의 평균 |
| 지연 (p50, p95) | 그 회차 문항 | 재시도 없는 회차의 문항을 모두 합친 것 |
| token, 비용 | 그 회차 값 | 측정 회차의 평균. 늘 40문항 기준이다 |

실험 전체에 쓴 비용은 회차를 모두 더해 따로 적는다.

### 지표

| 지표 | 정의 |
| --- | --- |
| repository 추출 일치율 | 평가가 낸 값 그대로. 분모는 늘 40이다 |
| 조건 추출 일치율 | 평가가 낸 값 그대로. kimi-max는 전체 평가 결과의 같은 지표를 쓴다 |
| p50, p95 지연 | 조건 추출 단계 소요 시간. 실패한 문항도 넣는다. timeout도 지연이다. 값을 작은 순으로 놓고 ⌈q·n⌉번째 값을 쓴다(nearest-rank, 보간 없음). 40문항이면 p95는 38번째다 |
| 재시도 문항 수 | 조건 추출 단계 호출 기록의 시도 횟수가 1보다 큰 문항 수. 1개 이상이면 그 회차에 "재시도 섞임"을 표시한다 |
| 실패 호출 수 | 성공하지 않은 호출 수와 실패 이유별 개수 |
| 입력·출력·reasoning token 합 | 아래 보정 규칙을 따른 값 |
| `usage` 보고율 | token 수가 있는 조건 추출 단계 호출 수 / 전체 호출 수 |
| 40문항 비용 | 보정한 token 합 × 조사 노트의 단가. 단가와 접근일을 README에 적는다 |

전체 평가인 kimi-max 결과에서는 조건 추출 단계(`stage`가 `plan`)의 호출 기록만 쓴다.

**출력 token 보정**

| 공급자 | 과금 출력 token |
| --- | --- |
| OpenAI | `completion_tokens` (reasoning 포함) |
| xAI | `completion_tokens + reasoning_tokens` (`completion_tokens`에 reasoning이 빠져 있다) |
| Moonshot | `completion_tokens`. reasoning token은 보고되지 않아 "-"로 둔다 |
| Google | 사전 확인의 원본 `usage`로 정한다. 아래 조건을 만족할 때만 정한다 |

- Google 규약은 원본 `usage`에서 reasoning token이 0보다 크고, `total_tokens`와 비교해 `completion_tokens`가 reasoning을 포함하는지 판별될 때만 정한다. 판별되지 않으면 Gemini 비용은 "알 수 없음"이다.
  - 평가 결과의 호출 기록은 세 숫자만 남겨 측정 호출에서는 판별할 수 없다. 이를 위해 평가 코드를 바꾸지는 않는다.
- 비용은 알 수 없는 값을 0이나 추정치로 채우지 않는다.
  - token 수가 None인 호출이 하나라도 있으면 그 회차의 비용은 "알 수 없음"이고, `usage` 보고율을 함께 적는다.
  - reasoning token이 보고되지 않는 공급자(Moonshot)도 과금 출력 token은 `completion_tokens`로 계산할 수 있으면 비용을 낸다.
- cached input 단가는 쓰지 않는다. 문항마다 prompt가 달라 cache 적중을 기대하지 않는다.

### 고르는 기준

roadmap 규칙을 숫자로 정한다.

1. **정확도 하한:** 두 일치율이 모두 kimi-max 기준선보다 2문항 넘게 떨어지지 않아야 한다. 두 번 이상 돈 설정은 회차 평균으로 판정한다.
2. **동점 묶음:** 하한을 넘은 설정 중 가장 낮은 p95를 찾고, `p95 ≤ 최소 p95 × 1.10`인 설정을 모두 묶는다.
3. **묶음 안에서 고르기:** 두 일치율의 합이 가장 높은 설정을 고른다. 그래도 같으면 40문항 비용이 낮은 쪽을 고른다. 비용이 "알 수 없음"인 설정이 끼면 비용으로 가르지 않고 둘 다 결과에 적은 뒤 결론 없음으로 둔다.
4. **재시도 확인:** 고른 설정의 지연에 재시도 섞인 회차만 있으면 확인 회차를 돌린다.
   - 확인 회차는 설정마다 최대 2번이다.
   - 확인 회차도 정확도 하한을 넘어야 한다. 그 일치율은 회차 평균에 넣는다.
   - 재시도 없는 회차가 생기면 지연을 그 회차들로 다시 계산하고 1번부터 다시 고른다.
   - 2번 안에 재시도 없는 회차가 없으면 그 설정은 지연을 판정할 수 없어 후보에서 빼고 1번부터 다시 고른다.
5. 후보가 하나도 남지 않으면 kimi-k3(운영 설정)를 유지한다.

## Testing Decisions

- **test seam은 하나다. 집계 함수(결과 JSON 목록 → 비교 표의 행)를 테스트한다.** 측정과 사전 확인은 유료 API를 부르므로 CI에서 돌리지 않는다.
- 좋은 테스트는 결과 JSON을 넣고 표의 값을 확인한다. 내부 helper는 테스트하지 않는다. 확인할 값은 아래와 같다.
  - p95
  - 재시도 문항 수
  - 공급자별 출력 token 보정
  - 비용
  - 하한 판정과 회차 평균
  - 동점 묶음(가장 낮은 p95 기준, 비교 순서와 무관)
  - 재시도 섞인 회차의 지연 제외
  - 알 수 없는 비용을 추정치로 채우지 않음
  - 결과 검증 실패(fake provider, 설정 불일치, 모드 불일치, 문항 집합 불일치)
- 결과 JSON 입력은 `make eval-plan`과 `make eval`의 결과 형식을 따른 작은 fixture로 만든다. `tests/fixtures/`의 기존 fixture 방식을 따른다.
- 실험 폴더 코드는 지금 CI의 test 경로 밖에 있다. 집계 테스트를 어디에 둘지는 구현 때 정한다. M0 `compare.py`처럼 테스트 없이 두지 않는다.
- `strict_json_schema`를 고치게 되면 아래를 테스트한다. `tests/recommend/test_llm.py`의 기존 schema 테스트를 선례로 따른다.
  - `"default": null`이 없어진다.
  - 모든 속성이 여전히 `required`에 있다.
  - Pydantic 모델은 바뀌지 않는다.
- `make lint`, `make test` 통과.

## Out of Scope

- 추천 단계 비교(M1-b). M1-a의 측정 설정 중 일부를 M1-b가 다시 쓰지만, 이 spec은 다루지 않는다.
- 운영 기본 설정(`.env.example`, 기본값)의 변경. 두 단계 조합을 M1-b 완료 판정에서 확인한 뒤에 바꾼다.
- 평가 report에 p95를 넣는 것. 이번에는 집계에서만 계산한다.
- `reasoning_effort` 최소 수준이 아닌 설정(`low` 이상)의 비교. kimi-k3만 예외로, 기준선(`max`)과 최소 수준(`low`)을 잰다.
- 여러 날에 걸친 반복 측정, 시간대별 지연 차이.
- Responses API 등 OpenAI 호환 Chat Completions가 아닌 endpoint.

## Further Notes

- **측정 전에 사용자가 할 일:**
  - Kimi는 누적 충전 Tier 1($10) 이상이 필요하다. Tier 0은 3 RPM이다.
  - OpenAI는 Tier 1 이상이 필요하다. Free tier는 이 모델들을 쓸 수 없다.
  - Gemini는 billing 계정을 연결한 Tier 1이 필요하다. 운영과 같은 조건이고, free tier는 입력을 학습에 쓴다.
  - xAI는 Tier 0으로 충분하다.
- 측정에는 수집과 색인이 끝난 DB가 필요하다. `--plan-only`가 DB의 repository 목록을 쓴다.
- Gemini의 OpenAI 호환 layer는 beta다. strict `json_schema`의 `anyOf` + `null` 처리가 문서에 없어 사전 확인 실패 가능성이 가장 높다.
- xAI Chat Completions는 legacy endpoint지만 지금은 동작한다. 바꾸지 않는다.

- ✅ 비교 입력이 고정되지 않음: repository 목록을 측정 전후로 기록하고, 40문항 모두 측정해야 하며, 문항 집합이 다르면 집계가 멈춘다(§입력 고정, §결과 검증). 입력이 다르면 모델 비교가 안 된다.
- ✅ token 계산 근거가 부족함: Gemini 규약은 판별될 때만 정하고, 알 수 없는 비용은 "알 수 없음"으로 두며 `usage` 보고율을 함께 적는다. 평가 코드는 바꾸지 않는다(§출력 token 보정). 모르는 비용으로 판단하면 안 된다.
- ✅ 경계 모델을 다시 돌려도 구제되지 않음: 두 일치율 중 하나라도 ±2문항 안이면 다시 돌리고, 회차 평균으로 판정한다(§측정 규칙). 한 번 흔들림으로 판정하면 안 된다.
- ✅ 회차별 집계 규칙이 없음: 지표마다 회차 합치는 규칙을 표로 정하고, 비용은 늘 40문항 기준으로 맞춘다(§회차 합치기). 회차 수가 다르면 비교가 불공정하다.
- ✅ 재시도 확인의 종료 조건이 없음: 확인 회차는 최대 2번, 지연은 재시도 없는 회차만 쓰고, 끝내 없으면 후보에서 뺀다(§고르는 기준). 재시도 섞인 결과는 믿을 수 없다.
- ✅ 지연 순위가 하나로 정해지지 않음: p95는 nearest-rank로 계산하고, 동점 묶음은 가장 낮은 p95의 110% 이내로 정한다(§지표, §고르는 기준). 비교 순서에 따라 결과가 바뀌면 안 된다.
- ✅ 기준선 측정 방식이 roadmap과 다름: kimi-max는 전체 평가로 재고, 그 결과를 M1-b 입력으로도 쓴다(§Solution, §측정 규칙). 기준선은 전체 평가로 재야 M1-b에서도 쓴다.
