# F14 단계별 LLM 설정

- 상태: 승인됨
- roadmap: `docs/roadmap.md` Phase 3 F14, M1

## 1. 목적

조건 추출 단계와 추천 단계에 서로 다른 LLM을 쓸 수 있게 한다.
M1(단계별 LLM 비교)이 쓸 평가 모드와 기록을 함께 만든다.

지금은 설정이 하나(`WHATFROM_LLM_*`)라 두 단계가 같은 모델을 쓴다.
두 단계는 하는 일과 정답 지표가 달라 따로 고를 수 있어야 한다.

## 2. 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 설정 단위 | 단계마다 base URL, 모델, API 키, 덧붙일 JSON | 공급자가 단계마다 다를 수 있다 |
| 비어 있을 때 | 공통 설정 `WHATFROM_LLM_*`을 쓴다 | 지금 `.env`와 테스트가 그대로 동작한다 |
| reasoning 설정 | 요청 본문에 덧붙일 JSON으로 받는다 | 파라미터 이름이 공급자마다 다르다(`reasoning_effort`, `thinking`, `enable_thinking`). 공급자 목록을 코드에 두지 않는다 |
| API 키 | 단계별 키 설정을 둔다. 공급자 이름으로 자동 선택하지 않는다 | 같은 이유. 비교 실험 스크립트가 공급자 키를 단계별 키에 넣어 실행한다 |
| timeout·재시도 | 공통 정책 그대로(120초, 429·5xx 최대 2회) | 운영과 같은 조건으로 잰다. 단계별 timeout은 F11-b에서 본다 |

## 3. 설정

| 설정 | 비었을 때 |
| --- | --- |
| `WHATFROM_PLAN_LLM_BASE_URL`, `WHATFROM_RECOMMEND_LLM_BASE_URL` | `WHATFROM_LLM_BASE_URL` |
| `WHATFROM_PLAN_LLM_MODEL`, `WHATFROM_RECOMMEND_LLM_MODEL` | `WHATFROM_LLM_MODEL` |
| `WHATFROM_PLAN_LLM_API_KEY`, `WHATFROM_RECOMMEND_LLM_API_KEY` | 설정하지 않았을 때만 `WHATFROM_LLM_API_KEY` (또는 `MOONSHOT_API_KEY`) |
| `WHATFROM_PLAN_LLM_EXTRA_BODY`, `WHATFROM_RECOMMEND_LLM_EXTRA_BODY` | 덧붙이지 않는다 |

- `plan`과 `recommend`는 `LLMProvider`의 메서드 이름과 같다.
- 단계별 API 키는 **설정하지 않았을 때만** 공통 키를 쓴다. 빈 값으로 설정하면 인증 헤더를 보내지 않는다.
  - 인증이 필요 없는 endpoint(로컬 Ollama 등)로 다른 공급자의 키가 나가지 않게 하기 위해서다.
  - 그래서 `.env.example`에는 단계별 키 줄을 주석으로 둔다. 빈 줄로 두면 "키 없음"이 된다.
- 덧붙일 JSON은 JSON 객체여야 한다. 객체가 아니거나 JSON이 아니면 시작할 때 실패한다.
- 덧붙일 JSON에 `model`, `messages`, `response_format`이 있으면 시작할 때 실패한다. 이 세 키는 코드가 정한다.
- 덧붙일 JSON은 응답 형식을 바꾸지 않는 공급자별 파라미터를 위한 것이다. 응답 형식을 바꾸는 키(`stream`, `n` 등)는 막지 않으며, 넣으면 첫 호출이 오류로 실패한다.
- `WHATFROM_LLM_PROVIDER=fake`이면 단계별 설정은 쓰지 않는다.

## 4. 구조

- `OpenAICompatibleProvider`가 덧붙일 JSON을 받아 요청 본문에 합친다.
- 단계마다 provider를 하나씩 만들고, 두 provider를 묶어 `LLMProvider`로 내놓는다. `plan()`은 조건 추출 단계 provider로, `recommend()`는 추천 단계 provider로 보낸다.
- 두 단계 설정이 같아도 provider를 둘 만든다. 연결 풀을 나눠도 문제가 없고, 분기가 줄어든다.
- API와 eval은 지금처럼 `get_provider`로 provider를 얻는다. 호출하는 쪽은 바뀌지 않는다.

## 5. LLM 호출 기록

M1은 재시도가 섞인 지연을 가려내고 비용을 계산해야 한다. 지금은 둘 다 남지 않는다.

- 호출마다 단계, 시도 횟수, 응답의 `usage`(입력·출력 token, 있으면 reasoning token)를 기록한다.
- **실패한 호출도 포함해 논리적 호출 하나당 기록을 정확히 하나** 남긴다. 재시도 소진, timeout, JSON이 아닌 응답, schema 검증 실패가 모두 해당한다.
  - 시도 횟수는 예외가 나도 전달돼야 한다. 반환값만으로 전달하면 실패한 호출의 시도 횟수가 사라진다.
  - `usage`는 schema 검증 전에 확보한다. 응답은 왔지만 검증에서 실패한 호출도 비용이 든다.
  - `usage`를 얻을 수 없으면 token 수를 `null`로 둔다.
  - 기록에는 성공 여부와 실패 이유를 함께 남긴다.
- provider에 호출 기록을 받는 콜백을 선택 인자로 둔다. eval은 문항마다 기록을 모아 결과 JSON에 싣는다. API는 콜백을 넘기지 않는다.
  - provider는 API에서 여러 요청이 함께 쓰므로, 마지막 호출 정보를 provider 속성에 두지 않는다.
- 재시도 횟수를 알려면 `post_json`이 성공과 실패 모두에서 시도 횟수를 알려 줘야 한다. 임베딩 쪽 호출자는 바뀌지 않게 한다.
- 비용 계산은 하지 않는다. 가격은 공급자마다 바뀌므로 M1 실험 스크립트가 token 수로 계산한다.

## 6. 평가 모드

지금 eval은 검색 전용(`--retrieval-only`)과 전체 두 모드다. 두 모드를 더한다. 네 모드는 함께 쓸 수 없다.

### 조건 추출 단계만 (`--plan-only`)

- 문항마다 조건 추출 단계만 부른다. 임베딩, 검색, 추천 단계는 부르지 않는다.
- 입력과 대상 문항은 전체 모드와 같은 규칙을 따른다. 그래야 두 모드의 추출 지표를 비교할 수 있다.
  - repository 목록은 전체 모드처럼 DB에 수집된 repository 이름 전체다. 프롬프트와 정규화(`normalize_plan`)에 같은 목록을 쓴다.
  - 필요한 repository가 색인되지 않은 문항은 전체 모드처럼 미측정으로 빼고 분모에서 제외한다.
- 지표: repository 추출 일치율, 조건 추출 일치율. 채점은 전체 모드와 같은 규칙을 쓴다.
- 문항별로 검색 조건, 필드별 일치, 조건 추출 단계 소요 시간, LLM 호출 기록을 남긴다.
- 추출에 실패한 문항은 두 지표 모두 실패로 센다.

### 검색 조건 고정 (`--plans <결과 JSON>`)

- 이전 전체 평가 결과에서 문항별 검색 조건을 읽어, 조건 추출 단계 대신 그 값을 쓴다. 나머지 경로(후보 생성, 추천 단계, 검증, 채점)는 전체 모드와 같다.
- 그 결과에서 추출에 실패한 문항(검색 조건이 `null`)은 이번에도 추출 실패로 다룬다. 같은 입력을 주기 위해서다.
- 아래 경우에는 모델을 부르기 전에 실패한다.
  - 결과 파일의 골든셋 해시가 지금 골든셋과 다르다.
  - 결과 파일이 전체 모드가 아니다.
  - 측정할 문항이 결과 파일에 없다.
- 결과 meta에 고정한 결과 파일 이름을 남긴다.
- 조건 추출 단계를 부르지 않으므로 추출 지표는 출력하지 않는다.

### 결과 meta

- `llm_model` 하나 대신 단계별 base URL, 모델, 덧붙일 JSON을 남긴다. API 키는 남기지 않는다.
- 부르지 않은 단계는 `null`이다.
- report의 모델 표시는 두 단계 모델이 같으면 하나로, 다르면 둘 다 보인다.

## 7. 범위 밖

- 비용 계산, 비교 실험 스크립트, 모델 선택: M1에서 한다.
- 단계별 timeout, 서킷브레이커, 캐시: F11-b에서 한다.
- OpenAI 호환이 아닌 API(Anthropic native 등): 이번에 비교하지 않는다.

## 8. 완료 판정

- 단계별 설정을 비워 두면 지금과 같은 요청 본문이 나간다(테스트로 확인).
- 두 평가 모드가 fake provider로 CI를 통과한다.
- 결과 JSON에 LLM 호출 기록과 단계별 meta가 남는다.
- `make lint`, `make test` 통과.
