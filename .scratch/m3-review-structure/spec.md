# M3 후보 비교표와 인용을 붙인 단일 선택의 비교

- Status: ready-for-agent
- roadmap: `docs/roadmap.md` Phase v2 M3
- 결정: `docs/adr/0003-judge-candidates-instead-of-recommending.md`
- 설계: `docs/design.md` §7, §8, §10
- 앞선 측정: `eval/experiments/2026-10-05-v2-first-run/README.md`

## Problem Statement

ADR 0003은 검토 단계를 후보 비교표로 할지, 인용을 붙인 단일 선택으로 둘지 측정 뒤에 정하기로 미뤘다. 지금은 그 비교를 할 수 없다.

- 판정 단계가 없다. 후보 비교표 안은 설계 문서에만 있다.
- golden set의 판단 요구 라벨은 어디에서도 읽지 않는다. 단일 선택 prompt는 질문, 후보, 근거만 받는다.
- V2 첫 측정에서 단일 선택의 인용 뒷받침률은 26/43(60.5%)로 합격선 90%에 못 미쳤다. 결론에 필요한 사실을 인용하지 않거나 일부만 인용한 주장이 많았다. 이것이 출력 구조의 문제인지, prompt의 문제인지 가를 측정이 없다.
- 판단 요구가 있는 문항과 없는 문항은 두 안에서 다르게 동작한다. 판정 단계는 판단 요구가 없으면 판정하지 않고 검색 1위를 추천한다. 그런데 지금 평가는 지표를 40문항 전체로만 낸다.
- 인용 검토 표본 도구는 주장만 읽고 문항당 2개로 고정되어 있다. 판정 칸을 진술로 뽑을 수 없고, 판단 요구가 있는 20문항에서 안마다 50개를 뽑을 수도 없다.

## Solution

두 안을 eval에서 고를 수 있게 만들고, 같은 입력으로 재서, 측정 전에 정한 기준으로 하나를 고른다.

- **판정 단계**: 후보마다 판단 요구 각각을 만족, 불만족, 알 수 없음으로 판정하고 인용 목록을 붙인다. 서버가 판정을 정규화하고 세 등급으로 순위를 정한다. eval에서만 부르고, `/recommend`는 바꾸지 않는다.
- **단일 선택 보강**: 판단 요구를 넘기고, 주장에 쓴 문서 사실마다 인용을 달라고 지시한다. 출력 구조는 그대로 둔다. 두 안에 같은 입력과 같은 인용 지시를 줘서, 차이가 구조에서 온다고 말할 수 있게 한다.
- **eval 확장**: 라벨 고정 입력에서 검토 방식을 고른다. 지표를 판단 요구가 있는 문항과 없는 문항으로 나눠서도 낸다. 판정 단계 실행에서는 오답 적발률, 오판정률, 미확인 1위 참고 정확도를 낸다.
- **인용 검토 표본 도구 확장**: 판정 칸을 진술로 읽는다. 문항당 상한과 표본 대상 문항을 option으로 고를 수 있게 한다.
- **측정과 결정**: 두 안을 luna-none으로 2회씩 돌리고, 1회차 결과에서 안마다 인용 50개를 검토한다. 아래 고르는 기준으로 하나를 고르고 ADR 0003과 설계 문서를 확정한다.

## User Stories

1. 평가를 돌리는 개발자로서, 라벨 고정 입력에서 검토 방식을 단일 선택과 판정 단계 중에 고르고 싶다. 그래야 두 안을 같은 후보와 근거로 잰다.
2. 평가를 돌리는 개발자로서, 검토 방식을 지정하지 않으면 지금처럼 단일 선택으로 돌기를 원한다. 그래야 기존 명령과 결과가 그대로 재현된다.
3. 평가를 돌리는 개발자로서, 라벨 고정 입력이 아닌 실행에서 판정 단계를 고르면 시작 전에 거부되기를 원한다. 그래야 판단 요구 없이 판정 단계를 돌린 결과를 얻지 않는다.
4. 평가를 돌리는 개발자로서, 결과 meta에 검토 방식이 남기를 원한다. 그래야 두 안의 결과 파일을 섞지 않는다.
5. 평가를 돌리는 개발자로서, 두 안이 같은 LLM 설정(검토 단계 설정)을 쓰기를 원한다. 그래야 모델 차이가 비교에 섞이지 않는다.
6. 평가를 돌리는 개발자로서, 판정 단계가 판단 요구를 golden set 라벨에서 받기를 원한다. 그래야 판단 요구 추출 품질이 판정 품질과 섞이지 않는다.
7. 평가를 돌리는 개발자로서, 단일 선택도 같은 판단 요구를 받기를 원한다. 그래야 판정 단계만 요구를 알고 있어서 생기는 차이가 없다.
8. 평가를 돌리는 개발자로서, 판단 요구가 없는 문항에서 단일 선택 prompt가 요구 없음을 분명히 보여 주기를 원한다. 그래야 LLM이 빈 목록을 누락으로 읽지 않는다.
9. 평가를 돌리는 개발자로서, 두 안의 prompt가 같은 인용 지시("주장이나 판정에 쓴 문서 사실마다 인용을 단다")를 담기를 원한다. 그래야 인용 뒷받침률 차이가 지시 차이에서 오지 않는다.
10. 평가를 돌리는 개발자로서, 판정 단계가 전체 후보(최대 20개)를 판정하기를 원한다. 그래야 정답이 검색 6위 아래인 문항에서 검색 순위가 결과를 정하지 않는다.
11. 평가를 돌리는 개발자로서, 판정 칸마다 인용 목록을 받고 싶다. 그래야 문장 두 개가 있어야 받쳐지는 판정이 구조적으로 불리하지 않다.
12. 평가를 돌리는 개발자로서, 후보 목록에 없는 후보나 범위 밖의 요구 번호를 가리키는 칸이 버려지기를 원한다. 그래야 LLM이 지어낸 참조가 비교표에 남지 않는다.
12-1. 평가를 돌리는 개발자로서, 없는 근거 번호를 가리키는 인용이 검증 실패로 세지고 그 칸이 알 수 없음으로 내려가기를 원한다. 그래야 지어낸 근거 번호가 인용 검증 통과율에 드러난다.
13. 평가를 돌리는 개발자로서, 같은 칸이 둘 이상이면 그 칸이 알 수 없음이 되기를 원한다. 그래야 서로 다른 판정 중 하나를 근거 없이 고르지 않는다.
14. 평가를 돌리는 개발자로서, 빠진 칸이 알 수 없음으로 채워지기를 원한다. 그래야 모든 후보가 모든 판단 요구에 대해 칸을 가진다.
15. 평가를 돌리는 개발자로서, 만족이나 불만족 판정에 인용이 없으면 알 수 없음으로 내려가기를 원한다. 그래야 근거 없는 확정 판정이 순위를 바꾸지 않는다.
16. 평가를 돌리는 개발자로서, 칸의 인용 중 하나라도 글자 그대로 검증에 실패하면 그 칸이 알 수 없음으로 내려가기를 원한다. 그래야 지어낸 인용이 섞인 판정을 내보내지 않는다.
17. 평가를 돌리는 개발자로서, 그 후보의 repository가 아닌 문서를 인용한 칸이 알 수 없음으로 내려가기를 원한다. 그래야 다른 이미지의 문서로 판정하지 않는다.
18. 평가를 돌리는 개발자로서, 정규화가 일어난 칸마다 이유가 남기를 원한다. 그래야 어떤 실패가 많은지 센다.
19. 평가를 돌리는 개발자로서, 후보가 확인됨, 미확인, 위반 세 등급으로 나뉘고 등급, 만족 수, 검색 순위 순으로 정렬되기를 원한다. 그래야 순위를 서버가 결정론적으로 정한다.
20. 평가를 돌리는 개발자로서, 추천이 확인됨 등급의 1위만 되기를 원한다. 그래야 인용 검증 실패로 불만족이 알 수 없음으로 내려간 후보가 추천되지 않는다.
21. 평가를 돌리는 개발자로서, 확인됨 후보가 없는 문항은 추천이 없고 오답으로 세기를 원한다. 그래야 설계 문서 §10의 정의와 같다.
22. 평가를 돌리는 개발자로서, 확인됨 후보가 없을 때 미확인 등급 1위를 추천으로 본 참고 정확도를 보고 싶다. 그래야 정확도가 낮을 때 원인이 판정 품질인지 "확인됨만 추천" 규칙인지 가른다.
23. 평가를 돌리는 개발자로서, 판단 요구가 없는 문항에서 판정 단계가 LLM을 부르지 않고 검색 1위를 추천하기를 원한다. 그래야 설계 문서 §7대로 동작한 값을 잰다.
24. 평가를 돌리는 개발자로서, 지표를 40문항 전체, 판단 요구가 있는 문항, 없는 문항으로 나눠 보고 싶다. 그래야 판정 단계가 요구 없는 문항에서 검색 1위 대조군에 묶이는 효과를 따로 본다.
25. 평가를 돌리는 개발자로서, 검색 1위 대조군도 같은 묶음으로 나눠 보고 싶다. 그래야 묶음마다 두 안이 대조군보다 나은지 본다.
26. 평가를 돌리는 개발자로서, 판정 단계 실행에서 오답 적발률과 오판정률을 보고 싶다. 그래야 명시적 오답을 불만족으로 잡는지, 허용 정답을 억울하게 떨어뜨리는지 안다.
27. 평가를 돌리는 개발자로서, 단일 선택 실행에서 오답 적발률과 오판정률이 미측정으로 나오기를 원한다. 그래야 판정이 없는 실행을 0%로 오해하지 않는다.
28. 평가를 돌리는 개발자로서, 두 안 모두 인용 검증 통과율을 보고 싶다. 판정 단계에서는 칸의 인용 전체가 분모다. 그래야 두 안이 근거를 글자 그대로 옮기는 정도를 비교한다.
29. 평가를 돌리는 개발자로서, 문항별 결과에 정규화한 후보 비교표(칸마다 판정, 인용과 검증 결과, 정규화 이유)와 후보별 등급이 남기를 원한다. 그래야 틀린 문항을 칸 단위로 들여다본다.
30. 평가를 돌리는 개발자로서, 판정 단계의 소요 시간과 token 사용량이 단일 선택과 같은 자리에 남기를 원한다. 그래야 지연과 비용을 같은 자로 비교한다.
31. 평가를 돌리는 개발자로서, 판정 단계 실행에서도 문항별로 LLM에 넘긴 prompt가 남기를 원한다. 그래야 인용 검토 도구가 후보 정보를 읽고, 입력이 같았는지 확인한다.
32. 인용 표본을 검토하는 개발자로서, 판정 칸을 진술로 뽑고 싶다. 진술은 "후보 X가 요구 R을 만족한다/어긴다"이고 이미지는 그 후보다. 그래야 두 안을 같은 기준으로 채점한다.
33. 인용 표본을 검토하는 개발자로서, 만족과 불만족 칸 중 검증을 통과한 인용이 있는 칸만 표본에 들어가기를 원한다. 그래야 알 수 없음 칸이나 이미 검증에 걸린 칸을 다시 보지 않는다.
34. 인용 표본을 검토하는 개발자로서, 판단 요구가 있는 문항에서만 표본을 뽑는 option을 원한다. 그래야 두 안의 표본이 같은 문항에서 나온다.
35. 인용 표본을 검토하는 개발자로서, 문항당 상한을 option으로 바꾸고 싶다(M3는 3). 그래야 판정 단계가 20문항에서도 50개를 채운다.
36. 인용 표본을 검토하는 개발자로서, option을 주지 않으면 V2와 같은 표본(전체 문항, 문항당 2개)이 나오기를 원한다. 그래야 V2 표본을 같은 seed로 재현한다.
37. 인용 표본을 검토하는 개발자로서, 두 안의 표본이 섞이고 안 이름이 가려지기를 원한다. 그래야 결과 파일 이름이나 설정으로 안을 알지 못한 채 채점한다.
37-1. 인용 표본을 검토하는 개발자로서, 한 안의 1회차 결과로 50개를 채우지 못하면 같은 안의 2회차 결과로 채우고 싶다. 그래야 인용을 단 주장이 적은 안도 표본 수가 줄지 않는다.
38. 인용 표본을 검토하는 개발자로서, 판정 칸 항목에도 후보 정보 대조(`candidate_ok`)를 채울 수 있기를 원한다. 그래야 후보 정보 오류를 두 안에서 같이 센다.
39. 실험을 기록하는 개발자로서, 고르는 기준이 측정 전에 실험 기록에 적혀 있기를 원한다. 그래야 결과를 본 뒤 기준을 맞추지 않는다.
40. 실험을 기록하는 개발자로서, 두 안을 같은 날(KST) 같은 고정 입력으로 2회씩 돌리고 싶다. 그래야 공급자 부하와 측정 흔들림이 한쪽에만 섞이지 않는다.
41. 실험을 기록하는 개발자로서, 인용 길이 분포와 판정 단계의 출력 token을 기록하고 싶다. 그래야 V3에서 인용 길이 규칙과 후보 수 상한을 정할 때 쓴다.
42. 프로젝트 유지자로서, M3 결론으로 ADR 0003의 Status와 설계 문서가 확정되기를 원한다. 그래야 V3가 무엇을 경로에 넣을지 안다.
43. 프로젝트 유지자로서, 판정 단계를 고르면 판단 요구가 없는 문항을 어떻게 다룰지 V3로 넘어가는 결정이 기록되기를 원한다. 그래야 요구 없는 문항이 검색 1위 대조군에 묶인 채로 경로에 들어가지 않는다.
44. 프로젝트 유지자로서, 이 측정이 모델 선택 근거가 아니라는 점과 luna-none 한 설정으로 잰 한계가 기록되기를 원한다. 그래야 M2에서 결론을 잘못 끌어오지 않는다.

## Implementation Decisions

**검토 방식 선택**

- eval에 검토 방식 option(단일 선택, 판정 단계)을 더한다. 기본값은 단일 선택이다.
- 판정 단계는 라벨 고정 입력에서만 고를 수 있다. 다른 mode와 함께 쓰면 시작할 때 거부한다. 판단 요구는 golden set 라벨에서만 오고, 판단 요구 추출은 V4의 일이다.
- 결과 meta에 검토 방식을 남긴다.
- HTTP `/recommend`는 판정 단계를 노출하지 않고, 응답 형식도 바꾸지 않는다. 단계 조합은 지금처럼 api와 cli만 한다(계층 규칙).

**판단 요구 전달**

- 판단 요구는 검색 조건과 별도의 입력으로 검토 단계에 넘긴다. `SearchPlan`에는 더하지 않는다. 더하면 조건 추출 단계의 출력 schema가 바뀌는데, 그것은 V4에서 판단 요구 추출과 함께 정한다.
- 라벨 고정 입력은 문항의 `requirements`를 검토 단계에 넘긴다. 다른 mode와 `/recommend`는 빈 목록을 넘긴다.

**단일 선택 보강**

- prompt에 판단 요구 목록을 번호와 함께 싣는다. 빈 목록이면 "판단 요구 없음"을 분명히 적는다.
- 인용 지시를 "주장에 쓴 문서 사실마다 그 사실을 담은 문장을 인용한다. 사실 하나에 문장이 둘 이상 필요하면 모두 인용한다"로 바꾼다. 판정 단계와 같은 문구를 쓴다.
- 출력 schema(`Recommendation`: 이미지, 대안, 주장 목록)는 바꾸지 않는다.
- 이 prompt는 `/recommend`의 단일 선택에도 그대로 쓰인다. 같은 단계의 prompt를 둘로 나누지 않는다. API 응답 형식은 바뀌지 않는다.
- 후보 줄의 형식은 바꾸지 않는다. 인용 검토 도구가 그 형식으로 후보 정보를 읽는다.

**판정 단계 계약**

- LLM 출력은 판정 목록이다. 판정 하나는 후보(후보 줄의 이미지 그대로), 판단 요구 번호, 판정(`satisfied`, `violated`, `unknown`), 인용 목록이다. 인용은 단일 선택과 같은 `Citation`(근거 번호, 글자 그대로의 문장)이다.
  - 설계 문서 §7의 `Judgment`는 근거 번호와 인용을 하나씩만 받는다. 이 spec은 인용 목록으로 바꾼다. M3에서 판정 단계를 고르면 설계 문서를 이 모양으로 고친다.
  - 판정 칸에는 이유 문장을 두지 않는다. 진술은 칸 자체("후보 X가 요구 R을 만족한다/어긴다")다.
- strict schema 변환과 Pydantic `extra="forbid"`는 기존 출력 모델과 같게 적용한다.
- `LLMProvider`에 판정 호출 메서드를 하나 더한다. 실제 provider(OpenAI 호환, Anthropic), 단계별 provider, fake provider, eval의 고정 조건 provider와 시간 측정 감싸기가 모두 이 메서드를 가진다.
  - LLM 설정은 검토 단계(지금의 `recommend` 단계) 설정을 쓴다. 단계 설정을 새로 만들지 않는다.
  - 호출 기록에는 판정 호출임을 구분할 수 있는 단계 이름을 남긴다.
  - 부하 측정용 모의 LLM은 바꾸지 않는다. 판정 단계는 HTTP 경로에 없다.
- prompt에는 질문, 번호를 붙인 판단 요구, 단일 선택과 같은 형식의 후보 줄, 같은 형식의 번호 붙은 근거를 싣는다. 모든 후보와 모든 판단 요구의 칸을 내라고 지시한다.

**판정 정규화와 순위**

- 설계 문서 §7의 정규화 규칙을 따르되, 인용을 목록으로 받는 데 맞춰 아래처럼 정한다.
  - 후보 목록에 없는 후보, 범위 밖의 요구 번호를 가리키는 칸은 버린다.
  - 인용이 없는 근거 번호를 가리키면 그 인용은 검증 실패로 본다.
  - 같은 (후보, 요구) 칸이 둘 이상이면 그 칸을 `unknown`으로 둔다. 그 칸에는 원래 판정들을 인용과 검증 결과까지 그대로 남긴다.
  - 빠진 칸은 `unknown`으로 채운다.
  - `satisfied`와 `violated`는 다음을 모두 만족할 때만 유지한다. 아니면 `unknown`으로 내린다.
    - 인용이 하나 이상 있다.
    - 모든 인용이 글자 그대로 검증을 통과한다(기존 인용 검증, 공백 정규화).
    - 모든 인용의 근거가 그 후보의 repository 문서다.
- 정규화가 일어난 칸에는 이유(버림, 중복, 빠짐, 인용 없음, 인용 검증 실패, 다른 repository)를 남긴다. 인용마다 검증 결과도 남긴다.
- 인용 검증 규칙(부분 문자열, 공백 정규화)은 바꾸지 않는다. 인용 길이 하한이나 문장 경계 규칙은 두지 않는다.
- 순위는 서버가 정한다.
  - 등급: 확인됨(불만족 없음, 모든 요구 만족), 미확인(불만족 없음, `unknown` 있음), 위반(불만족 하나 이상)
  - 정렬: 등급, 만족 수(내림차순), 검색 순위
- 추천은 확인됨 등급의 1위다. 확인됨 후보가 없으면 추천이 없다.
- 판단 요구가 없는 문항은 LLM을 부르지 않는다. 모든 후보가 확인됨이므로 검색 1위가 추천이다.
- 판정 단계의 LLM 호출이 실패하면 기존 저하 경로처럼 추천 없이 후보와 근거만 남기고 `degraded`로 표시한다. 재판정하지 않는다(설계 문서 §8).

**eval 결과와 지표**

- 판정 단계 실행의 문항 기록에 다음을 남긴다.
  - 정규화한 후보 비교표
  - 후보별 등급
  - 미확인 1위
  - 불만족 판정을 받은 후보 목록(지금 비어 있는 `unsatisfied_candidates`)
- 오답 적발률과 오판정률은 기존 집계를 그대로 쓴다. 단일 선택 실행에서는 지금처럼 미측정이다.
  - 판정한 문항만으로 센다. 판단 요구가 없는 문항과 판정 호출이 실패한 문항은 `unsatisfied_candidates`를 `None`으로 두어 분모에서 뺀다. `[]`는 판정했지만 불만족 후보가 없다는 뜻이다.
  - 판정 호출이 실패한 문항 수를 두 지표 옆에 낸다. 그 문항은 추천 정확도에서 이미 오답으로 세진다.
- 참고 정확도: 추천이 있으면 추천, 없으면 미확인 1위를 추천으로 보고 같은 허용 규칙으로 채점한다. 판정 단계 실행에서만 낸다.
- 인용 검증 통과율은 단일 선택에서는 주장의 인용 전체, 판정 단계에서는 LLM이 낸 판정 중 버리지 않은 것(중복 포함)의 인용 전체를 분모로 센다. 중복 칸을 정규화로 어떻게 합치든 값이 같다. 인용 길이 분포도 같은 인용으로 센다.
- 지표 묶음: 추천 정확도, 검색 1위 대조군, 참고 정확도, 인용 검증 통과율을 40문항 전체, 판단 요구가 있는 문항, 없는 문항으로 나눠서도 낸다. 묶음은 golden set의 `requirements`가 비었는지로 정한다. 다른 지표는 전체로만 낸다.
- 검토 단계의 소요 시간, prompt, LLM 호출 기록은 지금 단일 선택이 쓰는 자리를 그대로 쓴다. 판정 단계에서 LLM을 부르지 않은 문항은 호출 기록이 비고 소요 시간이 0에 가깝다. 지연은 실험 기록에서 묶음별로 따로 계산한다.

**인용 검토 표본 도구**

- 결과 파일에 판정 칸이 있으면 칸을 진술로 읽는다. 대상은 `satisfied`와 `violated` 중 검증을 통과한 인용이 있는 칸이다. 진술 문장은 도구가 "<후보>가 요구 '<판단 요구>'를 만족한다/어긴다" 꼴로 만든다. 진술이 가리키는 이미지는 그 후보다.
- 판정 칸 항목도 진술의 인용 전체를 한 항목으로 본다. 채점 단위와 기준(`verdict`, `candidate_ok`)은 V2와 같다.
- 표본 생성에 세 option을 더한다.
  - 문항당 상한. 기본값은 지금 값(2)이다.
  - 판단 요구가 있는 문항만 쓰기. 기본값은 끔이다. 문항의 판단 요구는 결과 파일과 같은 golden set에서 읽는다.
  - 결과 파일 여러 개를 한 안으로 묶기. 앞 파일에서 먼저 뽑고, 50개가 안 되면 다음 파일에서 채운다. 문항당 상한은 묶은 안 전체에 적용한다. 기본값은 지금처럼 파일 하나가 한 안이다.
- key 항목마다 원래 결과 파일과 진술 위치를 남긴다. 위치는 주장이면 주장 번호, 판정 칸이면 후보와 판단 요구 번호다. 묶은 파일들에서 같은 문항, 같은 위치가 나와도 항목을 가를 수 있어야 한다.
- 안당 표본 수(50), seed, 안 이름 가리기, 채점 집계와 합격선(90%)은 바꾸지 않는다.

**측정 절차**

- 입력: 라벨 고정 입력. golden set은 지금 버전을 고치지 않는다.
- 모델: 두 안 모두 `gpt-6-luna`, `reasoning_effort: none`(luna-none). embedder는 V2 첫 측정과 같다.
- 두 안을 같은 날(KST)에 2회씩 돌린다. 회차마다 단일 선택부터 돌린다.
- 네 실행 모두 40문항을 재고 건너뛴 문항이 없어야 한다. 아니면 그 실행을 무효로 둔다. 정확도 기준(2문항)은 요구 있는 20문항을 모두 잰다는 전제다.
- 측정하는 동안 수집과 색인을 돌리지 않는다. 네 실행의 문항별 후보 목록과 근거 목록(번호, repository, 섹션)을 비교해, 다른 문항이 있으면 그 회차를 무효로 두고 다시 잰다.
- 정확도는 2회 평균으로 판정한다. 인용 검토는 두 안의 1회차 결과로 하고, 50개가 안 되면 같은 안의 2회차 결과로 채운다.
  - 표본: 판단 요구가 있는 문항만, 문항당 최대 3개, 안당 50개, seed 0
- 기록할 것:
  - 위 지표 전부(묶음별 포함)
  - 정규화 이유별 칸 수
  - 인용 길이 분포
  - 묶음별 검토 단계 p95
  - 판정 단계의 출력 token
  - 비용
- 결과는 `eval/experiments/<날짜>-m3-review-structure/`에 남긴다. 측정 전에 아래 고르는 기준을 그 README에 먼저 적는다.

**고르는 기준**

1. 단일 선택이 기본값이다. 판정 단계는 아래 두 조건을 모두 만족할 때만 고른다.
2. 인용 뒷받침률: 판정 단계가 합격선(90%)을 넘고 단일 선택은 못 넘는다. 또는 판정 단계가 단일 선택보다 20%p 넘게 높다. 20%p는 표본 50개씩일 때 두 비율 차이의 대략적인 95% 오차다. 한 문항에서 여러 진술을 뽑으므로 실제 오차는 더 클 수 있고, 이 점은 실험 기록의 한계에 적는다.
   - 2회차로 채운 뒤에도 어느 한쪽의 채점 가능한 진술이 30개 미만이거나, 채점 결과가 보류나 미측정이면 이 조건을 만족하지 못한 것으로 본다.
3. 추천 정확도: 판단 요구가 있는 문항에서 판정 단계의 2회 평균이 단일 선택보다 2문항 넘게 낮지 않다.
4. 판정 단계를 고르면, 판단 요구가 없는 문항은 V3에서 단일 선택으로 넘기는 혼합 구조로 처리한다. 판단 요구가 없는 문항의 정확도는 이 결정에 쓰지 않는다.
5. 지연과 비용은 기록만 하고 판정에 쓰지 않는다.

**결정 반영**

- ADR 0003의 Status와 Consequences를 M3 결론으로 확정한다.
- 단일 선택을 고르면 설계 문서 §1, §2, §4, §5, §7, §8을 단일 선택 기준으로 고친다(ADR 0003의 마지막 줄).
- 판정 단계를 고르면 설계 문서 §7의 `Judgment`를 인용 목록으로 고치고, 정규화 규칙 전체를 이 spec과 맞추고, 판단 요구가 없는 문항의 혼합 구조를 적는다.
- roadmap의 M3 절에 결과를 적고, V3 절을 고른 안에 맞게 고친다.
- 판정 단계가 탈락하면 판정 단계 코드와 테스트, eval의 판정 단계 선택 option을 결과 기록 뒤의 커밋에서 지운다. 인용 검토 도구의 option과 지표 묶음은 남긴다.

## Testing Decisions

좋은 테스트는 공개된 입구로 들어가 밖에서 보이는 결과만 확인한다. 내부 함수 이름, prompt 문구, 정렬 구현은 확인하지 않는다. 경우의 수는 표 형태(parametrize)로 고정한다.

**seam 1: eval CLI 종단 (fake provider)**

- 라벨 고정 입력에 판정 단계를 골라 돌리고, 결과 JSON으로 다음을 확인한다.
  - meta의 검토 방식
  - 추천과 등급
  - 판정 칸
  - `unsatisfied_candidates`
  - 오답 적발률과 오판정률
  - 참고 정확도
  - 묶음별 지표
- 판단 요구가 없는 문항에서 LLM 호출이 없고, 검색 1위가 추천인지 확인한다.
- 검토 방식을 생략하면 지금과 같은 단일 선택 결과가 나오는지 확인한다.
- 판정 단계를 라벨 고정 입력 밖에서 고르면 거부되는지 확인한다.
- 단일 선택에서 판단 요구가 prompt로 넘어가는지 확인한다. 라벨 고정 입력에서는 문항의 요구가 넘어가고, 다른 mode에서는 요구가 없음을 확인한다. prompt 기록에 판단 요구 문장이 있는지 정도만 본다.
- 인용 검토 도구: 판정 단계 결과와 단일 선택 결과에서 표본을 뽑아 다음을 확인한다.
  - 판정 칸 진술
  - 판단 요구가 있는 문항만 쓰는 option
  - 문항당 상한 option
  - 결과 파일 여러 개를 한 안으로 묶는 option
  - option 없이 뽑으면 V2와 같은 표본
- 기존 예: `tests/test_cli_eval.py`의 라벨 고정 입력 테스트와 `sample-citations`·`score-citations` 왕복 테스트, `tests/eval/test_citations.py`

**seam 2: 검토 단계 함수 (recommend 패키지, fake provider)**

- 입력은 질문, 판단 요구, 후보, 번호 붙은 근거, provider다. 출력은 정규화한 후보 비교표, 등급, 추천이다.
- 정규화 규칙을 경우마다 고정한다.
  - 후보 목록 밖의 칸, 범위 밖 요구 번호
  - 없는 근거 번호
  - 중복 칸, 빠진 칸
  - 인용 없는 확정 판정
  - 인용 일부 검증 실패
  - 다른 repository의 근거
- 순위를 경우마다 고정한다.
  - 세 등급 정렬
  - 만족 수 동점일 때 검색 순위
  - 확인됨이 없으면 추천 없음
  - 판단 요구가 없으면 LLM을 부르지 않고 검색 1위
- LLM 호출 실패 시 저하 동작을 확인한다.
- 판정 출력 모델의 strict schema(중첩 `$defs` 포함)와, 각 provider가 판정 호출을 기존 호출과 같은 방식으로 보내고 기록하는지를 기존 provider 테스트 방식으로 확인한다.
- 기존 예: `tests/recommend/test_verify.py`(parametrize 인용 검증), `tests/recommend/test_advisor.py`(fake provider), `tests/recommend/test_llm.py`(strict schema, 호출 기록, Anthropic)

CI는 네트워크와 API 비용 없이 통과해야 한다. 실제 측정은 수동이다.

## Out of Scope

- `/recommend` 경로와 응답 형식 변경, MCP server(V3, V6)
- 판단 요구 추출과 구조화 힌트(V4)
- 판단 요구가 없는 문항의 혼합 구조 구현(판정 단계를 고르면 V3)
- 판정 대상 후보 수와 판단 요구 수의 상한(V3에서 출력 token과 지연을 재서 정한다)
- 인용 검증 규칙 변경(인용 길이 하한, 문장 경계)
- 모델 비교와 선택(M2). M3는 luna-none 한 설정만 쓴다
- 검색 보강과 `node-arm64-graviton`, `alpine-static-binary`(V5)
- golden set 라벨 수정
- 판정 실패 시 재판정
- 부하 측정용 모의 LLM에 판정 호출 추가

## Further Notes

- 판정 단계는 판단 요구가 없는 20문항에서 구조상 검색 1위 대조군과 같은 값을 낸다(V2 첫 측정 기준 대조군 27/40). 그래서 40문항 전체 정확도는 고르는 기준에 쓰지 않고, 묶음별로 나눠 본다.
- 단일 선택 prompt 보강은 `/recommend`에도 반영된다. V2 첫 측정(60.5%)과 M3의 단일 선택 값은 prompt가 달라 직접 비교하지 않는다.
- luna-none은 reasoning이 꺼져 있다. 판정 단계처럼 칸이 많은 출력에서 불리할 수 있다. 이 한계는 실험 기록에 적고 M2에서 다룬다.
- 판정 단계의 칸 수는 최대 40개(후보 20개 × 요구 2개)다. 출력이 잘리면 OpenAI 호환 provider에서는 JSON 검증이 실패하고, Anthropic provider에서는 `stop_reason`으로 실패한다. 그 문항은 저하로 기록된다. OpenAI 호환 provider는 `finish_reason`을 보지 않으므로, 측정 전 사전 확인에서 판정 칸이 가장 많은 문항의 `finish_reason`을 직접 본다.
- 판정 칸 진술은 고정 형식이고 단일 선택의 주장은 자유 문장이라, 이름을 가려도 형식으로 안을 알아볼 수 있다. 채점 기준이 "진술에 쓰인 문서 사실이 인용으로 확인되는가"라서 편향 위험은 작다고 보고, 실험 기록의 한계에 적는다.
