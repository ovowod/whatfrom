# 판단 요구 라벨과 명시적 오답 보강 (V2, 2026-10-05)

**결론: golden set에 판단 요구를 넣고, 명시적 오답을 필수 요구 위반만 남도록 고쳤다. 검색 1위 대조군은 27/40이고 보강 전후로 같다.**

- 명시적 오답이 후보에 나온 문항은 16에서 10으로 줄었지만, 후보로 나온 명시적 오답은 28개에서 84개로 늘었다. 오답 적발률은 후보 단위로 세므로 분모는 84다.
- 문항 수가 준 것은 크기 선호를 근거로 한 reject를 뺐기 때문이다. 판정 단계가 후보 하나만 보고 잡을 수 없는 오답이었다.
- 후보 목록, 후보 포함률, 문서 Hit@5, 두 대조군은 보강 전후로 같다. M1-b의 luna-none 두 회차와 kimi-max-r1의 추천을 새 라벨로 다시 채점해도 정확도는 37로 같다.

## 판단 요구 라벨

- subagent가 질문만 보고 초안을 썼고(accept, reject, rationale을 보지 않음), 그 초안을 근거와 대조해 고쳤다. 검토 표는 `requirements-review.md`다.
- 초안은 LTS, stable 브랜치, 정식 릴리스, Linux 이미지 여부를 "버전 필터"로 보고 뺐다. 검색 조건에는 버전 접두어만 있어 이것들은 판단 요구로 더했다.
- 초안의 "설치하면 되는 것" 요구(빌드 도구, gcc, ca-certificates)는 뺐다. 근거가 오답이 아니라고 적은 후보를 불만족으로 만든다.
- 명시적 오답을 검토하며 두 요구를 더했다: python-latest-stable의 "가장 새 정식 줄기", temurin-jdk-build-stage의 "Gradle이 도는 Java 17 이상". python-fastapi-prod에는 "정식 릴리스"를 더했다.
- 결과: 20문항에 요구가 있고 20문항은 빈 목록이다.

## 명시적 오답 보강

검토 표는 `reject-review.md`다.

- 더한 태그: 기존 reject와 같은 근거로, 라벨 고정 입력의 후보에 나온 다른 버전과 별칭 태그(9문항)와 B절의 두 문항.
- 뺀 태그: 크기 선호(6문항), 묻지 않은 변형(1문항), 질문이 요구하지 않은 latest와 prerelease(8문항), 차이만 묻는 문항의 이동 suite 이름(1문항). 뺀 이유는 각 문항의 rationale에 적었다.
- 남긴 판단: 질문이 버전 유지나 특정 릴리스를 요구하는 문항의 latest는 태그가 옮겨 가는 것 자체가 위반이라 남겼다. postgres:15는 rationale대로 accept에서만 빼고 reject에 넣지 않았다.
- accept 태그와 digest가 같은 태그는 넣지 않았다. 허용 정답은 고치지 않았다.

## 한계

- 근거 URL을 모두 다시 열지 않았다. 더한 reject는 문항에 이미 적힌 근거를 다른 태그로 넓힌 것이다. 그래서 golden set의 `verified_on`은 그대로다.
- 라벨 고정 입력의 후보에 나온 태그만 봤다. 운영 경로(조건 추출 단계를 거친 후보)에서만 나오는 태그는 검토하지 않았다.
