# whatfrom roadmap

무엇을 어떤 순서로 만드는지 적는다. 시스템이 어떻게 생겼는지는 [설계 문서](design.md)에 있다.

## 원칙

- **수직 슬라이스(Walking Skeleton):** 얇지만 끝까지 관통하는 경로를 먼저 만든다. 그 뒤 각 feature가 그 경로의 한 구간을 깊게 판다.
- **feature 단위:** 각 feature는 1~3일 단위이고, 완료 판정이 있다.
- **자를 먼저 만든다:** 측정 harness는 그 harness로 잴 개선 작업보다 항상 먼저 온다. baseline이 없으면 개선을 증명할 수 없다.
- **매번 다시 잰다:** feature마다 eval을 다시 돌려 점수를 기록한다. 이 기록이 프로젝트 결과의 본문이 된다.

## 항목 계열

| 계열 | 뜻 | 결과를 남기는 곳 |
| --- | --- | --- |
| F | 기능을 만드는 feature | 코드, README 측정 결과 |
| V | Phase v2(후보 비교표)의 feature. F와 같다 | 코드, README 측정 결과 |
| M | 결정을 내리기 위한 측정 실험. 코드를 바꾸지 않을 수도 있다 | `eval/experiments/<날짜>-<주제>/` |

## 현재 위치

Phase 3을 멈추고 **Phase v2(후보 비교표)** 로 설계를 바꿨다([ADR 0003](adr/0003-judge-candidates-instead-of-recommending.md), [설계 문서](design.md)). 다음은 **V1(계약과 골격)** 이다.

- F16에서 Dockerfile 초안의 질을 재려다, 질문만으로는 잴 가치가 낮은 산출물에 측정 장치만 커진다는 것을 확인했다.
- 주 사용자를 LLM agent로 보고 Dockerfile 생성을 뺀다. 두 번째 LLM 호출은 근거 인용을 검증하고, 후보 비교표와 인용을 붙인 단일 선택 중 무엇으로 할지 M3에서 비교해 정한다.
- M1-b(추천 단계의 LLM 비교)는 운영에 반영하지 않는다. 판정 단계의 모델은 M2에서 다시 고른다.
- F11-b, F12, F13은 판정 단계의 지연과 실패 양상을 본 뒤 Phase v2 뒤에서 다시 설계한다.

### F10: 부하 기준선 (완료)

**완료 판정:** 0.2→2 RPS 스파이크에서 아래 값을 README에 기록한다.

- Kimi 실측 분포(배율 1.0)와 빠른 LLM 분포(배율 0.1) 각각의 시작 구간별 p50/p95/p99와 추천 성공률(표본 수 포함)
- 완료 구간별 처리량
- `dropped_iterations`

**결과:** 모의 LLM으로 기준선을 쟀다. 스파이크 성공률은 Kimi 실측 분포에서 6.9%, 빠른 LLM 분포에서 100%다.
동기 핸들러와 응답 직렬화가 같은 스레드 풀(40개)을 두 번 기다렸다. 그래서 서버가 끝낸 일 대부분이 클라이언트 timeout 뒤에 나갔다(`load/results/`, README "부하 측정").

### F11: 캐시와 장애 대응 (일부만 완료)

**F11은 끝나지 않았다.** 동시성 제한(F11-a)만 끝났고, 캐시와 서킷브레이커(F11-b)는 시작하지 않았다.

원래 범위는 "캐시 + timeout·재시도·서킷브레이커·동시성 제한"이다.
timeout과 재시도는 Phase 0에서 이미 넣었다. 남은 것을 둘로 나눴다.

| 항목 | 범위 | 상태 |
| --- | --- | --- |
| F11-a | 비동기 `/recommend` + 추천 작업 수 상한. 모델과 무관한 구조 개선 | 완료 |
| F11-b | 캐시(임베딩·결과) + 서킷브레이커. 고른 모델의 속도와 실패 양상을 보고 설계한다 | M1 뒤에 시작 |

**F11-a를 먼저 한 이유:** F10에서 서버가 끝낸 일 대부분이 클라이언트 timeout 뒤에 나가는 문제가 드러났다.
이 문제를 풀려면 F11 범위 중 동시성 제한이 필요했고, 이 부분은 어떤 LLM을 쓰든 같다.

**F11-a 결과:** `/recommend`를 비동기로 바꿔 응답 검증이 스레드 풀을 다시 기다리지 않게 했다.
추천 작업 수 상한(32)을 넘는 요청은 503으로 거절한다.
Kimi 실측 분포에서 헛일 0%, 스레드 대기 p95 0.05초, 회복 구간 성공률은 4.9% → 96.7%다.

### F14: 단계별 LLM 설정 (완료)

조건 추출 단계와 추천 단계에 서로 다른 LLM을 쓸 수 있게 하고, M1에 필요한 평가 모드를 만든다.

- 단계마다 base URL, 모델, API 키, 요청 본문에 덧붙일 JSON을 따로 둔다. 비어 있으면 공통 설정 `WHATFROM_LLM_*`을 쓴다.
- 평가에 두 모드를 더한다. 조건 추출 단계만 돌리는 모드와, 이전 결과의 검색 조건을 고정해 추천 단계만 돌리는 모드다.
- 평가 결과에 LLM 호출마다 재시도 횟수와 token 사용량을 남긴다.

**완료 판정:** 설정을 비워 두면 지금과 같은 요청이 나가고, 두 평가 모드가 fake provider로 CI를 통과한다.

**결과:** 조건 추출 단계만 재는 `make eval-plan`과, 검색 조건을 고정하고 추천 단계만 재는 `make eval-recommend PLANS=<결과 JSON>`을 만들었다.
단계별 설정은 빈 값도 설정하지 않은 것으로 본다. API 키만 예외로, 빈 값이면 인증 header를 보내지 않는다.
LLM 호출 기록에는 실패한 호출도 하나씩 남는다.

### F15: Anthropic native provider (완료)

M1-b에 Claude Sonnet을 넣기 위해, 단계마다 LLM API 종류를 고르고 Anthropic native Messages API로 부를 수 있게 한다.
Anthropic의 OpenAI 호환 layer는 `response_format`과 `reasoning_effort`를 무시해 비교 조건을 만들 수 없다([조사 노트](research/2026-10-03-m1b-recommend-stage.md)).

- 단계별 설정 `WHATFROM_PLAN_LLM_API`, `WHATFROM_RECOMMEND_LLM_API`(`openai_compatible`, `anthropic`)를 둔다. 비우면 지금과 같다.
- Anthropic provider도 같은 인터페이스와 같은 호출 기록을 낸다. thinking과 effort는 `EXTRA_BODY`로 정한다.

**완료 판정:** API 종류를 비워 두면 지금과 같은 요청이 나가고, Anthropic 요청·응답·실패 처리가 가짜 transport 테스트로 CI를 통과한다.

**결과:** `WHATFROM_RECOMMEND_LLM_API=anthropic`이면 추천 단계가 `/v1/messages`로 간다. 결정은 [ADR 0002](adr/0002-anthropic-via-native-messages-api.md)에 있다.

- `EXTRA_BODY`의 `thinking`과 `output_config.effort`는 schema와 병합한다. 코드가 정하는 키와 객체가 아닌 `output_config`는 시작할 때 막는다.
- 출력이 잘리거나(`max_tokens` 16,000) 모델이 거부하면 그 이유로 실패하고 호출 기록을 남긴다. 529(과부하)도 재시도한다.
- 실제 Anthropic API는 아직 부르지 않았다. M1-b 사전 확인에서 처음 부른다.

### M1: LLM 모델 비교

LLM 지연을 줄일 모델을 단계마다 고른다. 두 단계는 하는 일과 정답 지표가 달라 따로 비교한다.
kimi-k3는 reasoning을 끌 수 없어, 지연의 대부분이 reasoning token에서 나오는 것으로 본다.
지금은 `reasoning_effort`를 보내지 않아 기본값 `max`로 돌고, 가장 낮은 값은 `low`다.
모델별 reasoning 설정과 가격은 [조사 노트](research/2026-10-03-m1-llm-candidates.md)에 있다.

**공통 규칙**

- kimi-k3 기준선은 비교 대상 모델과 같은 시기에 전체 평가로 다시 잰다. 기준선은 운영 설정(`max`)으로 잰 값이다.
- kimi-k3도 다른 모델처럼 reasoning 최소 수준(`low`)으로 따로 재서 후보에 넣는다.
- 모델마다 1회 돌리고, 정확도 하한 ±2문항 안에 든 모델만 한 번 더 돌린다.
- timeout(120초)과 재시도(429·5xx 최대 2회)는 운영과 같게 둔다. 재시도가 섞인 결과의 지연은 신뢰할 수 없다고 표시한다.
- **고르는 기준:** 1. 성능(지연, 정확도) 2. 비용 순서로 본다.
  - 정확도 하한을 넘은 모델 중 가장 빠른 p95와의 차이가 기준선 요청 전체 p95의 5% 안이면 성능이 비슷한 것으로 본다.
  - 성능이 비슷한 모델 중 비용이 가장 낮은 모델을 고른다. 가장 싼 비용의 110% 안이면 비용이 같은 것으로 보고 정확도가 높은 쪽을 고른다.
  - M1-a 결과를 본 뒤 정했다. 처음 규칙은 비용을 기록만 했다.
- 결과는 `eval/experiments/<날짜>-<주제>/`에 남긴다. kimi-k3를 유지하는 결론도 될 수 있다.

**M1-a: 조건 추출 단계**

- **비교 대상 모델:** kimi-k3(기준선 `max`, 후보 `low`), `gpt-6-luna`, `grok-4.3`, `gemini-3.5-flash-lite`. 각 모델의 reasoning 최소 수준으로 잰다.
  - 1·2회차 결과를 본 뒤 `gpt-6-luna` `low`와 `gpt-6.1-sol` `low`를 추가했다. 고른 kimi-k3 `low`보다 훨씬 싼 GPT에 reasoning을 조금 준 설정이 비교 대상에 없었다.
- **정확도 하한:** repository 추출 일치율과 조건 추출 일치율이 kimi-k3 기준선보다 2문항 넘게 떨어지지 않는다.

**M1-a 결과:** 조건 추출 단계에 `gpt-6-luna` + `reasoning_effort: low`를 쓴다. 기준선 말고 정확도 하한을 넘은 설정은 이것 하나다. 운영 설정은 M1-b 완료 판정 뒤에 바꾼다.
이 결론은 M1-b 완료 판정에서 뒤집혔다. luna-low의 repository 추출은 7회 평균 34.9로 하한 35 아래였다. 조건 추출 단계는 kimi-k3를 유지하고 M1-c에서 다시 고른다.

- 기준선 kimi-k3(`max`)보다 조건 추출 단계 p95가 24.1초 → 4.6초, 40문항 비용이 $0.303 → $0.0075로 준다.
- 정확도는 5회 평균 repository 추출 35.4, 조건 추출 38.2로 하한(35, 38)을 넘는다. 조건 추출은 0.2문항 차이로 넘었다.
- 처음 기준선이 fake embedder로 돌아 다시 쟀다. 다시 잰 기준선은 정확도가 1문항씩 높아, kimi-k3 `low`와 `gpt-6.1-sol` `low`가 하한에 못 미치게 됐다.
- 고르는 기준을 공통 규칙(성능이 비슷하면 비용)으로 고쳤다. 처음 규칙은 비용을 거의 보지 않았다. 다시 잰 기준선에서는 어느 규칙으로도 결과가 같다.
- golden set의 `alpine-static-binary` 라벨과, repository를 도구나 언어로만 암시하는 문항의 채점을 다시 봐야 한다.

자세한 내용은 [실험 기록](../eval/experiments/2026-10-03-plan-llm-comparison/README.md)에 있다.

**M1-b: 추천 단계**

- **비교 대상 모델:** M1-a의 4개에 `gpt-6.1-sol`과 `claude-sonnet-5-5`를 더한다. kimi-k3를 뺀 모델은 reasoning 최소 수준과 `low` 두 가지로 잰다.
  `claude-sonnet-5-5`는 F15의 Anthropic provider로 부른다. 최소 수준은 `{"thinking": {"type": "between_tools"}, "output_config": {"effort": "low"}}`, `low`는 `{"output_config": {"effort": "low"}}`다.
  `gpt-6.1-sol`은 `none`과 `minimal`이 없어 최소 수준이 `low`이므로 한 번만 잰다.
- **입력 고정:** M1-a의 `results/kimi-max-r1.json`(실제 embedder로 다시 잰 전체 평가)에서 검색 조건 40개를 가져와 `eval --plans`로 고정한다.
  후보와 근거는 다시 검색하므로, 문항별 추천 단계 prompt가 이 파일의 `advise_prompt`와 하나라도 다르면 그 결과는 무효다.
  채점이 측정 시점 DB의 digest를 쓰므로, 회차 전후에 repository 목록과 허용 정답 태그 digest를 기록해 다르면 그 회차를 무효로 둔다.
- **기준선:** `kimi-max-r1`의 추천 단계 결과를 그대로 쓰지 않는다. 지연은 공급자 부하에 따라 달라지므로, kimi-k3 `max`도 같은 고정 입력으로 다른 모델과 같은 시기에 다시 잰다.
  - 같은 시기는 한 측정 회차의 모든 설정을 하루(KST) 안에 이어서 재는 것이다. 회차마다 kimi-k3 `max`부터 잰다.
  - `kimi-max-r1`은 고정 입력의 출처이고, 5% 기준의 바탕인 요청 전체 p95(`seconds_total`)도 이 파일 값을 상수로 쓴다.
- **지연 지표:** 추천 단계 소요 시간(`seconds_advise`)의 p95로 비교한다. 결과 기록에는 `kimi-max-r1`의 추천 단계 p95에 M1-a에서 고른 설정의 조건 추출 단계 p95를 더한 값을 바탕으로 한 판정도 함께 적는다.
- **측정 전에 할 것:**
  - 측정 도구가 `--embedder`를 항상 지정하고, 결과 meta의 embedder와 embedding model이 `kimi-max-r1`과 다르면 결과를 무효로 둔다.
  - eval에 문항 사이 대기 option을 더한다. 기본값은 0이고, 429가 난 공급자(Gemini)에만 AI Studio의 RPM 한도로 계산한 간격을 준다. 대기 시간은 지연에 넣지 않는다.
  - 사전 확인은 설정마다 입력이 가장 큰 문항(`temurin-17-jammy-pinned`)으로 한 번 부른다. 출력이 잘리거나 거부되면 측정을 시작하지 않는다.
- **정확도 하한:** 추천 정확도 35/40 이상. 지금 golden set(`fe366444`)에서 kimi-k3가 낸 최저치다. 측정마다 2~3문항씩 흔들리므로 기준선(37/40)을 하한으로 두지 않는다.
  태그 실재율, 출처 제공률, verify 거부는 기록만 하고, 기준선보다 나빠진 설정은 결과 기록에 표시한다. 두 회차 이상이면 정확도는 회차 평균으로 판정하고, 지연은 재시도 없는 회차만으로 계산한다. 비용을 몰라 비교할 수 없으면 판정을 보류한다.
- **golden set은 고치지 않는다.** M1-a가 의심한 `alpine-static-binary`와, 모든 모델이 틀린 `node-arm64-graviton`은 라벨이 아니라 검색과 근거 문서 문제였다(F17).
- **429 본문과 `finish_reason`은 사전 확인에서만 본다.** 운영 코드의 실패 처리는 F11-b에서 설계한다.
- **완료 판정:** 두 단계에서 고른 설정 조합을 전체 평가로 한 번 돌려, repository 추출 35, 조건 추출 38, 추천 정확도 35를 모두 넘는지 확인한다.
  넘으면 `.env.example`의 단계별 예시와 README를 고른 설정으로 바꾼다. 코드 기본값은 그대로 둔다.

**M1-b 결과:** 추천 단계에 `gpt-6-luna` + `reasoning_effort: none`(luna-none)을 고른다. 운영 설정은 F16 뒤에 바꾼다.

- 추천 정확도 2회 평균 37로 kimi-k3 `max`와 같고, 추천 단계 p95는 87.9초에서 3.4초, 40문항 비용은 약 $1.33에서 $0.018로 준다.
- 완료 판정: luna-low + luna-none은 repository 추출 2회 평균 33.5로 미달이다. kimi-k3 `max` + luna-none은 35, 39, 37로 통과했고 요청 전체 p95는 20.9초다.
- 11개 설정 모두 추천 정확도가 35~38문항이고, reasoning을 켜도 꺼도 같다. 두 문항은 모든 설정이 틀려 실질적인 천장이 약 38이다.
- Dockerfile 초안의 질은 재지 않았다. luna-none의 Dockerfile은 kimi-k3보다 짧고 실행 명령이 없거나 맞지 않는 경우가 있다.

자세한 내용은 [실험 기록](../eval/experiments/2026-10-04-recommend-llm-comparison/README.md)에 있다.

### F16: Dockerfile 초안 품질 지표 (취소)

Dockerfile 초안의 품질 기준과 judge LLM을 설계하다가 취소했다. 질문 한두 문장으로는 진입점, 의존성 파일, 포트를 알 수 없어, 초안의 질은 잴 가치가 낮았다.
Dockerfile 생성 자체를 빼기로 했다([ADR 0003](adr/0003-judge-candidates-instead-of-recommending.md)).

### F17: 검색과 근거 문서 보강

Phase v2의 V5로 옮겼다. 아래는 옮기기 전에 정리한 문제다.

M1-b의 20번 측정에서 모든 설정이 틀린 두 문항을 고친다. golden set은 고치지 않는다.

- `alpine-static-binary`: 질문에 이미지 이름이 없으면 조건 추출 단계가 repository를 비우고, 벡터 검색이 정답 alpine을 후보에 넣지 못한다.
- `node-arm64-graviton`: 정답의 근거(arm64 musl 빌드는 Experimental)가 색인하는 `docker-library/docs`에 없고 `nodejs/docker-node` README에 있다. 이 문서를 쓰려면 ADR 0001을 다시 본다.

**완료 판정:** 두 문항의 정답이 후보와 근거에 들어가고, 전체 평가의 다른 지표가 떨어지지 않는다.

### M1-c: 조건 추출 단계 재선정

Phase v2의 M2로 옮겼다. 아래는 옮기기 전에 정리한 관찰이다.

kimi-k3 + luna-none 조합에서 남은 지연의 대부분은 조건 추출 단계다(요청 전체 p95 20.9초 중 17.6초).

- 고르는 기준을 측정 전에 정한다. M1-b 완료 판정에서 repository 추출이 32로 떨어져도 추천 정확도는 37이었다. 추출 일치율이 최종 추천의 질과 맞지 않을 수 있다.
- 후보는 M1-a의 결과를 참고한다. luna-low(p95 4.6초)와 kimi-low(8.1초)가 하한 근처였다.

### F12: 큐와 워커

**완료 판정:** 과부하에서 p99가 유계이고, 정상 요청 성공률을 유지한다.

과부하는 M1에서 고른 LLM의 처리량을 넘도록 스파이크를 키워 만든다. 기준은 큐 없이 503이 나기 시작하는 지점이다.
빠른 LLM에서는 0.2→2 RPS 스파이크로는 몰림이 생기지 않아, 큐의 효과가 보이지 않기 때문이다.

### V1: 공통 골격

M3에서 어느 안을 고르든 필요한 것만 만든다.

- Dockerfile 생성을 뺀다. `Recommendation.dockerfile`, `pin.py`, Dockerfile 이미지 참조 검증을 지우고, 후보마다 `image@digest` 참조를 준다.
- 근거에 요청 안에서만 쓰는 번호를 붙이고, 응답에 그 번호와 본문을 담는다.
- 인용 검증을 만든다. 인용이 그 요청에서 넘긴 근거 본문 안에 글자 그대로 있고(공백 정규화) 그 후보의 repository 문서인지 본다.
- 외부 사용자가 없으므로 `/recommend` 경로는 그대로 둔다.

**완료 판정:** 응답 형식과 인용 검증을 계약 테스트로 고정하고, fake provider로 CI와 `make eval`이 돈다.

### V2: 평가 v2, 판단 요구 라벨, 기준선

- [설계 문서](design.md) §10의 지표를 만든다.
- golden set 문항마다 기대 판단 요구 목록을 라벨로 넣는다. 질문만 보고 쓰고 사람이 검토한다. 후보 하나만 보고 판정할 수 있는 요구만 쓴다.
- 명시적 오답 라벨이 오답 적발률의 분모가 되므로, 라벨이 부족한 문항을 보강한다. 허용 정답은 고치지 않는다.
- 인용 뒷받침률은 judge LLM 없이, 표본을 사람이 확인하는 도구로 잰다. M3와 V3에서 쓸 합격선을 측정 전에 정한다.

**완료 판정:** `make eval`이 v2 지표를 내고, 판정 없이 검색 순위만 쓴 추천 정확도를 기준선으로 README에 기록한다.

### M3: 후보 비교표와 인용을 붙인 단일 선택의 비교

ADR 0003에서 미룬 결정이다. 두 안을 모두 만들고 같은 입력으로 잰다.

- 입력 고정: 검색 조건과 판단 요구는 V2의 라벨로 고정하고, 후보와 근거는 같은 검색 결과를 쓴다.
- 두 안 모두 같은 인용 검증을 거친다. LLM은 같은 모델과 설정을 쓴다.
- 지표: 추천 정확도, 인용 뒷받침률(사람 표본), 인용 검증 통과율, 지연, 비용. 고르는 기준은 측정 전에 정한다.

**완료 판정:** 둘 중 하나를 고르고, 그 결과로 ADR 0003과 설계 문서를 확정한다.

### V3: 채택한 구조의 판정과 인용 검증

- M3에서 고른 구조를 실제 경로에 넣는다. 후보 비교표라면 [설계 문서](design.md) §7의 정규화 규칙과 세 등급 순위를 따른다.
- 평가는 V2의 판단 요구 라벨을 고정해 두 번째 LLM 호출만 잰다. 요구 추출 품질과 섞지 않는다.
- 상위 후보 수와 판단 요구 수의 상한은 출력 token과 지연을 재서 정한다.

**완료 판정:** 다음을 모두 만족한다.

- 판정하거나 인용한 칸이 0보다 많다.
- 추천 정확도가 V2 기준선보다 낮지 않다.
- 인용 뒷받침률이 V2에서 정한 합격선을 넘는다.
- 오답 적발률, 오판정률, 인용 검증 통과율을 기록한다.

### V4: 구조화 힌트와 판단 요구 추출

- 요청에 선택적인 구조화 힌트를 받는다. 필드가 없으면 추론하고, 있으면 `null`이나 `[]`이라도 확정값으로 쓴다. 질문과 어긋나면 힌트를 따른다.
- 조건 추출 단계가 판단 요구를 영어 문장 목록으로 뽑는다. V2의 판단 요구 라벨을 정답으로 판단 요구 추출을 잰다.

**완료 판정:** 힌트를 준 평가 모드에서 추천 정확도가 질문만 준 평가 이상이고, 판단 요구 추출 지표를 기록한다.

### V5: 검색 보강

F17의 두 문항을 흡수한다.

- repository를 정하지 못하면 repository마다 따로 검색해 각자의 가장 가까운 근거로 후보에 넣을지 정한다. 지금은 상위 chunk에 나온 repository만 후보가 되어 `alpine-static-binary`에서 alpine이 빠진다. 할당 규칙은 측정해 정한다.
- 이미지마다 upstream 문서를 색인 대상에 더한다(`node-arm64-graviton`의 `nodejs/docker-node`). 받을 문서와 방법을 정한 뒤 [ADR 0001](adr/0001-readme-from-docker-library-docs.md)을 대체하는 ADR을 쓴다.
- 영어 검색 문장을 따로 뽑아 검색할지도 여기서 측정해 정한다.

**완료 판정:** 기록된 실패 입력(`alpine-static-binary`)에서 alpine 후보가 들어오고, 두 문항의 정답이 후보와 근거에 들어가며, 전체 평가의 다른 지표가 떨어지지 않는다.

### M2: 두 LLM 호출의 모델 선택

M1의 공통 규칙(성능 다음 비용)을 따른다. 고르는 기준과 정확도 하한은 측정 전에 v2 지표로 다시 정한다.
M1-c의 관찰(조건 추출 일치율이 최종 품질과 맞지 않을 수 있다)을 기준을 정할 때 반영한다.
