# 0003. Dockerfile 생성을 빼고, 두 번째 LLM 호출의 모양은 비교 실험으로 정한다

- Status: accepted (Dockerfile 제거). 두 번째 LLM 호출의 모양은 roadmap M3에서 정한다
- Date: 2026-10-05

## Context

v1은 두 번째 LLM 호출(추천 단계)이 후보 중 하나를 고르고, 이유, 대안, Dockerfile 초안을 썼다.

F16에서 Dockerfile 초안의 품질을 재려다 두 문제가 드러났다.

- 입력이 질문 한두 문장이라 진입점, 의존성 파일, 포트를 알 수 없다. Dockerfile은 추측이 섞인 초안일 수밖에 없다.
  그 초안을 재려고 문항 라벨, 규칙 parser, judge LLM, judge와 사람 라벨의 대조까지 쌓게 됐다. 잴 가치가 낮은 산출물에 측정 장치가 더 커졌다.
- 주 사용자로 보는 LLM agent는 프로젝트 파일을 직접 읽는다. Dockerfile은 그쪽이 더 잘 쓴다.
  agent가 혼자 얻기 어려운 것은 실재하는 태그, 아키텍처별 digest와 크기, 공식 문서의 근거다.

M1-b에서는 11개 설정의 추천 정확도가 모두 35~38문항이었고, 두 문항은 모든 설정이 틀렸다. 이 천장은 검색과 근거 문서의 한계에서 왔다.
추천 구조를 바꾼다고 풀리는 문제가 아니다. 검색 보강(roadmap V5)이 풀 문제다.

## Decision

- Dockerfile 생성을 뺀다. 후보마다 `image@digest` 참조를 주고, Dockerfile은 호출하는 쪽이 쓴다.
- 두 번째 LLM 호출의 근거 인용을 결정론적으로 검증한다. 인용은 그 요청에서 넘긴 근거 본문 안에 글자 그대로 있어야 한다.
- 두 번째 LLM 호출의 모양은 아래 두 안을 같은 입력으로 비교해 정한다(roadmap M3). 비교 지표는 추천 정확도, 인용 뒷받침률, 지연, 비용이다.
  - **후보 비교표**: 상위 후보마다 판단 요구 각각을 판정하고 인용한다. 순위는 서버가 정한다. 설계 문서는 이 안을 적는다.
  - **인용을 붙인 단일 선택**: 지금처럼 하나를 고르되, 이유를 검증된 인용으로 뒷받침한다.

## Considered Options

- **비교 없이 후보 비교표로 바꾼다.** 처음에는 이렇게 정했다. 받는 쪽이 크기와 안정성 같은 선호를 스스로 적용하려면 후보별 사실과 판정이 필요하다는 이유였다.
  하지만 판정 구조가 단일 선택보다 품질이 낫다는 측정은 없다. 단일 선택도 검증된 인용을 붙이면 받는 쪽이 근거를 확인할 수 있다.
  구현과 지연이 더 드는 안을 근거 없이 고르지 않는다.
- **판정 단계 없이 후보와 근거만 돌려준다.** 가장 단순하고 빠르다. 하지만 agent가 매번 README 절을 읽고 비교해야 하고, 이 시스템이 측정하고 개선할 판단 품질이 사라진다.
- **인용이 판정을 뒷받침하는지 LLM으로 검사한다.** F16의 judge와 같은 구조라 judge 자체를 다시 검증해야 한다. 뒷받침 여부는 평가에서 사람이 표본으로 확인한다.

## Consequences

- API 응답 형식이 바뀐다. `Recommendation.dockerfile`, Dockerfile의 `FROM` 고정(`pin.py`), Dockerfile 이미지 참조 검증이 사라진다.
- 불변식이 "이미지를 지어내지 않는다"에서 "이미지도 인용도 지어내지 않는다"로 넓어진다. 결정론적 검증이 보장하는 것은 인용의 진위까지이고, 인용이 판정을 뒷받침하는지는 평가에서 잰다.
- M1-b(추천 단계의 LLM 비교) 결과는 Dockerfile을 함께 쓴 작업을 잰 것이라 두 번째 LLM 호출의 모델 선택에 쓰지 않는다.
- 비교할 두 안을 모두 만들어야 하므로 V3 전에 실험 비용이 든다.

M3 결과 후보 비교표를 고르지 않으면 설계 문서의 §1, §4, §5, §7과 이 ADR을 고친다.
