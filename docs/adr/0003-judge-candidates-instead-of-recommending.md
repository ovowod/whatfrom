# 0003. 추천 1개 대신 후보 비교표를 돌려준다

- Status: accepted
- Date: 2026-10-05

## Context

v1은 두 번째 LLM 호출(추천 단계)이 후보 중 하나를 고르고, 이유, 대안, Dockerfile 초안을 썼다.

F16에서 Dockerfile 초안의 품질을 재려다 두 문제가 드러났다.

- 입력이 질문 한두 문장이라 진입점, 의존성 파일, 포트를 알 수 없다. Dockerfile은 추측이 섞인 초안일 수밖에 없다.
  그 초안을 재려고 문항 라벨, 규칙 parser, judge LLM, judge와 사람 라벨의 대조까지 쌓게 됐다. 잴 가치가 낮은 산출물에 측정 장치가 더 커졌다.
- 주 사용자로 보는 LLM agent는 프로젝트 파일을 직접 읽는다. Dockerfile은 그쪽이 더 잘 쓴다.
  agent가 혼자 얻기 어려운 것은 실재하는 태그, 아키텍처별 digest와 크기, 공식 문서의 근거다.

M1-b에서는 11개 설정의 추천 정확도가 모두 35~38문항이었다. "하나를 맞혔나"라는 지표로는 설정 간 차이를 가리지 못했다.

## Decision

- Dockerfile 생성을 뺀다. 후보마다 `image@digest` 참조를 주고, Dockerfile은 호출하는 쪽이 쓴다.
- 두 번째 LLM 호출은 **판정 단계**가 된다. 상위 후보마다 판단 요구 각각을 만족, 불만족, 알 수 없음으로 판정하고 근거 chunk를 인용한다. 후보를 고르지 않는다.
- verify는 후보의 실재성에 더해, 인용 문장이 넘겨준 근거 chunk 안에 글자 그대로 있는지 결정론적으로 검사한다. 실패한 칸은 알 수 없음으로 내린다.
- 순위는 서버가 판정 결과로 정한다. 순위 1위를 추천이라고 부른다.
- 호출하는 쪽은 질문과 함께 구조화 힌트(검색 조건과 판단 요구)를 보낼 수 있다. 조건 추출 단계는 빈 칸만 채운다.

## Considered Options

- **Dockerfile만 빼고 추천 1개를 유지한다.** 가장 작은 변경이다. 하지만 agent에게 하나의 선택과 이유 한 문단은 근거를 다시 확인할 수 없는 결론이고, 지표 포화도 그대로 남는다.
- **판정 단계 없이 후보와 근거 chunk만 돌려준다.** 가장 단순하고 빠르다. 하지만 agent가 매번 README 절을 읽고 비교해야 하고, 이 시스템이 측정하고 개선할 판단 품질이 사라진다.
- **인용이 판정을 뒷받침하는지 LLM으로 검사한다.** F16의 judge와 같은 구조라, judge 자체를 다시 검증해야 한다. 뒷받침 여부는 평가에서 사람이 표본으로 확인한다.

## Consequences

- API 응답 형식이 바뀐다. `Recommendation.dockerfile`, Dockerfile의 `FROM` 고정(`pin.py`), Dockerfile 이미지 참조 검증이 사라진다.
- 추천 정확도의 이력은 이어지지만 뜻이 바뀐다. v1은 LLM이 고른 것이고 v2는 판정에서 나온 순위 1위다. v2 기준선을 새로 잰다.
- M1-b(추천 단계의 LLM 비교) 결과는 다른 작업을 잰 것이라 판정 단계의 모델 선택에 쓰지 않는다.
- 판정 단계의 출력은 후보 수 × 판단 요구 수에 비례해 늘어난다. 상한은 측정해 정한다.
- 불변식이 "이미지를 지어내지 않는다"에서 "이미지도 근거도 지어내지 않는다"로 넓어진다.

다음 경우에는 이 결정을 다시 본다: 인용 검증 실패율이 높아 비교표 대부분이 알 수 없음이 될 때, 또는 판정 단계의 지연이 요청 지연의 대부분을 차지해 줄일 방법이 없을 때.
